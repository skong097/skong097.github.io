다중 로봇 관제 시스템을 만들었다. 로봇 여러 대의 상태를 한 화면에 띄우고, 죽은 로봇은
회색 점으로 표시한다. 흔한 구성이다.

며칠 전 그 회색 점 하나 때문에 40분을 추궁당했다. 질문은 딱 하나였다.

> **"몇 초 동안 안 오면 회색으로 칠합니까?"**

나는 **"2초?"** 라고 답했다.

코드를 열어보니 **3.0초**였다.

---

## 1. 내가 만든 것

로봇마다 agent가 돌면서 콘솔로 heartbeat를 쏜다.

```python
# wasab_robot_agent/agent_node.py
HEARTBEAT_HZ = 2.0                       # 초당 2번

def _hb_qos():
    q = QoSProfile(depth=10)
    q.reliability = QoSReliabilityPolicy.BEST_EFFORT   # ← 이 한 줄이 뒤에서 문제가 된다
    return q
```

콘솔은 heartbeat와 ping 두 신호를 보고 상태를 정한다.

```python
# wasab_gui/fleet.py
ROBOT_STALE_S = 3.0

def liveness_state(ping_ok, hb_fresh):
    if hb_fresh:
        return "online"     # ●  정상
    if ping_ok:
        return "powered"    # ◐  전원은 켜졌는데 agent가 죽음
    return "offline"        # ○  회색 점
```

신호가 2개면 조합은 4개인데 상태는 3개다. 하나가 어딘가로 흡수됐다는 뜻이다.

여기까지가 설계다. 나쁘지 않다고 생각했다.

---

## 2. 무너진 지점

압박 면접 형식으로 질문을 받았다. 결과는 이랬다.

| 물어본 것 | 내 대답 | 실제 |
|---|---|---|
| 몇 초 만에 offline인가 | **"2초?"** | **3.0초** (`ROBOT_STALE_S`) |
| 왜 그 값인가 | — | **답 못 함. 근거가 존재하지 않음** |
| 여러 개를 기다리는 이유는 | "무선이라 유실된다. 1개로 판정하면 오탐" | ✅ |
| **그 유실은 사고인가, 네가 만든 건가** | **"내가 임계치를 그렇게 설정함"** | ❌ |
| 4조합인데 왜 3상태인가. 남는 하나는 | "ping 있고 heartbeat 없는 경우" | ❌ **반대** |

세 번째 줄까지는 괜찮았다. 네 번째부터가 문제다.

### 2-1. "임계치를 내가 설정했다"는 틀린 답이다

질문은 *"heartbeat가 빠지는 게 네트워크 사고냐, 네가 그렇게 설계한 거냐"* 였다.
나는 "임계치를 내가 정했다"고 답했다.

**임계치는 유실에 *대응하는* 값이지 유실의 *원인*이 아니다.**

원인은 위에 있다. `BEST_EFFORT`.

```python
q.reliability = QoSReliabilityPolicy.BEST_EFFORT
```

`RELIABLE`이면 DDS가 재전송한다. `BEST_EFFORT`는 재전송하지 않는다. 빠지면 그냥 사라진다.
**유실은 사고가 아니라 내가 고른 것이다.** 그리고 그 선택 때문에 임계값이라는 것이 필요해졌다.

인과의 방향이 반대였다. 나는 결과를 원인이라고 말했다.

### 2-2. 정답이 내 코드 주석에 있었다

4조합 중 사라진 하나를 물었을 때 나는 `ping O + heartbeat X`라고 답했다. 틀렸다.
그건 `powered`다 — 사라지기는커녕 **가장 값진 상태**다. "SSH로 붙어서 agent만 다시 띄우면 된다"와
"현장에 사람이 가야 한다"를 갈라주는 칸이기 때문이다.

사라진 건 `ping X + heartbeat O`다. 이건 `online`으로 흡수된다.

이유는 이렇다. **heartbeat가 도착했다는 사실 자체가 "네트워크도 살아 있고 agent도 살아 있다"는
더 강한 증거다.** 약한 증거(ping 실패)로 그걸 뒤집지 않는다.

그리고 이 문장은 내가 이미 써놨다.

```python
def liveness_state(ping_ok, hb_fresh):
    """heartbeat가 오면 ping 무관하게 online(더 강한 신호). 그다음 ping만 있으면
    powered(전원켜짐·agent대기), 둘 다 없으면 offline."""
```

**"더 강한 신호"** 라고 내 손으로 적어놓고, 면접에서는 반대로 답했다.

---

## 3. 이게 왜 무서운가

못 배운 것이 아니다. **내가 만든 것을 내가 못 지킨 것**이다.

면접관은 남의 지식을 묻지 않는다. **내가 제출한 코드와 문서를 들고 묻는다.** 거기서
"제가 그렇게 짰던가요"가 나오면 그 프로젝트 전체의 신뢰가 무너진다. 모르는 걸 모른다고 하는 것보다
**아는 것을 틀리게 기억하는 쪽이 훨씬 위험하다.**

그리고 `3.0`이라는 숫자에는 아직도 근거가 없다. 코드에는 있는데 문서에는 없다.
누가 왜 3.0으로 정했는지 아무도 모른다. 나도 모른다. 내가 정했는데.

---

## 4. 업계는 이 문제를 이미 풀어놨다

내가 만든 3상태 판정은 결국 이 질문 하나였다.

> **"값이 안 온다"와 "죽었다"를 어떻게 구분하는가?**

산업 현장 표준인 **Sparkplug B**(MQTT 위에 얹는 규격)가 이 문제를 정면으로 다룬다.
방식은 내 heartbeat 폴링과 완전히 다르다.

| 메시지 | 뜻 |
|---|---|
| `NBIRTH` / `DBIRTH` | **출생 신고.** 접속 직후, 전체 태그 목록과 현재값을 한 번에 선언 |
| `NDATA` / `DDATA` | 이후에는 **변경분만** 전송 |
| `NDEATH` / `DDEATH` | **사망 신고** |
| `NCMD` / `DCMD` | 하향 명령 |

핵심은 `NDEATH`다. 노드는 접속할 때 브로커에 **"내가 갑자기 사라지면 이 메시지를 대신 뿌려달라"**
고 유언을 등록해둔다(MQTT의 Last Will). 그래서 죽으면 **브로커가 대신 부고를 알린다.**

내 방식과 비교하면 이렇다.

| | 내 heartbeat 방식 | Sparkplug B |
|---|---|---|
| 죽음 판정 | 콘솔이 **시간을 세어 추측**한다 | 브로커가 **명시적으로 통보**한다 |
| 임계값 | **필요하다** (그래서 `3.0`이 나왔다) | 원리적으로 불필요 |
| 무변화 vs 죽음 | **구분 못 한다** | 구분된다 |

내가 40분간 답하지 못한 그 질문이, 규격에는 이미 답으로 못 박혀 있었다.
(규격 쪽 이야기는 [OPC UA가 구조를 잡고 MQTT가 나른다](../제조-로봇-통합관제-데이터-02-opcua-mqtt-sparkplug/) §5에 더 자세히 정리해 뒀다.)

## 5. 그런데 공짜가 아니다

여기서 오늘 하나 더 틀렸다.

같은 날, 이런 상황을 받았다.

```text
로봇 12대 중 3대가 대시보드에 아예 안 나온다.
브로커 정상. 그 3대는 현장에서 멀쩡히 가동 중.
브로커를 직접 구독해보면 그 3대의 DDATA가 초당 몇 건씩 흐르고 있다.
대시보드를 껐다 켜도 똑같다.
```

나는 "agent가 살아 있는지, heartbeat에 이상이 없는지 확인한다"고 답했다.
**내 시스템에서 하던 짓을 그대로 꺼낸 것이다.** 그리고 그 확인은 전부 통과한다. 문제는 그대로다.

답은 이거였다.

> **`NBIRTH`는 retained message가 아니다.**

`NBIRTH`는 **한 번 발행되고 지나가는 메시지**다. 브로커가 붙들고 있다가 나중에 온 구독자에게
건네주지 않는다. 그런데 이후의 `NDATA`에는 태그 **이름이 없다** — 대역을 아끼려고 숫자 alias만 실린다.

```text
NBIRTH  { "metrics": [ {"name": "Axis1/Torque", "alias": 7, ...}, ... ] }
NDATA   { "metrics": [ {"alias": 7, "value": 23.4} ] }     ← alias 7이 뭔지 모름
```

그 3대는 대시보드가 구독을 시작하기 **전부터 계속 붙어 있었다.** 끊긴 적이 없으니 `NBIRTH`를
다시 뿌릴 이유가 없었다. 그래서 대시보드는 그 3대의 데이터를 받고도 **해석할 수 없다.**
대시보드를 재시작해도 소용없다. 다시 시작되는 건 대시보드지 엣지 노드가 아니니까.

고치려면 `NCMD`로 **rebirth를 요청**해서 노드가 `NBIRTH`를 다시 뱉게 해야 한다.

정리하면 이렇다.

> **죽음을 명시적으로 알게 된 대가로, 탄생에 의존하게 된다.**
> 부고는 받지만, 출생 신고를 놓치면 그 존재를 아예 모른다.

내 heartbeat 방식은 정반대의 성질을 갖는다. 죽음은 추측해야 하지만, **언제 붙어도 다음 heartbeat 한 번이면
전부 복구된다.** 늦게 접속한 구독자 문제가 원리적으로 없다.

어느 쪽이 낫다는 얘기가 아니다. **둘은 다른 것을 포기했다.**

---

## 6. 남은 것

- `ROBOT_STALE_S = 3.0` 의 근거를 문서화한다. 지금은 코드에만 있고 이유가 없다.
  `BEST_EFFORT` + 2Hz에서 3.0초는 **연속 6개 유실**을 뜻한다. 6이 맞는 숫자인지 아직 못 정했다.
- QoS를 `RELIABLE`로 바꾸면 이 값을 올려야 하는지 내려야 하는지 — 아직 자신 있게 답 못 한다.
- 내가 쓴 주석을 내가 못 지킨 사건이 한 번 더 나오면, 그건 우연이 아니다.

---

## 배운 것 세 줄

1. **유실은 사고가 아니라 QoS 선택의 결과다.** 임계값은 원인이 아니라 대응이다.
2. **강한 증거는 약한 증거로 뒤집지 않는다.** heartbeat가 도착했으면 ping 실패는 무시한다.
3. **내 코드에 적힌 것을 내가 모르면, 그건 안 만든 것과 같다.**
