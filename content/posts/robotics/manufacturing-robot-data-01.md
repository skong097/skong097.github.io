로봇을 운용하는 제조 현장에 통합 관제(integrated monitoring & control)를 구축한다고 하면,
가장 먼저 부딪히는 질문은 "무슨 도구를 쓸까"가 아니다.

> **"애초에 무슨 데이터를 다루게 되는가?"**

이걸 안 정하고 제품부터 고르면, 제품이 데이터 모델을 결정해버린다. 그게 가장 비싼 실수다.

이 글은 그 질문에 답하려고 정리한 조사 노트다. 데이터의 **종류 · 수집 방식 · 주기 · 보관 ·
파이프라인**, 그리고 그것을 강제하는 **표준과 법규**까지 다룬다.

프로토콜(OPC UA · MQTT · Sparkplug B) 상세는 분량이 커서 [2편](../제조-로봇-통합관제-데이터-02-opcua-mqtt-sparkplug/)으로 뺐다.

---

## 0. 먼저, 읽는 법 — 검증 등급을 붙인다

이 글의 모든 수치와 주장에는 등급을 붙였다.

| 등급 | 의미 |
|:---:|---|
| **A** | 표준 문서 · 법령 원문 · 규제기관 문서에 명시된 사실 |
| **B** | 복수의 벤더/업계 문서가 일치하는 통용 수치 |
| **C** | 단일 출처 또는 내 추론. **그대로 설계 근거로 쓰지 말 것** |

왜 이런 짓을 하냐면, **근거의 강도를 문장 안에서 구분하지 않으면 읽는 쪽이 전부 같은 무게로
받아들이기 때문**이다. "진동은 25kHz로 샘플링한다"와 "SCADA 폴링은 보통 1초"는 근거의 급이 전혀
다른데, 그냥 나열하면 둘 다 사실처럼 보인다.

그리고 미리 못 박아둘 것 하나.

> ⚠️ **이건 웹 문헌 조사다. 특정 공장의 실측이 아니다.**
> 아래 수치는 *설계 착수 시점의 출발 범위*이지 *우리 현장의 값*이 아니다.
> 실제 도입 시 1순위 작업은 **현장 태그 실측**(태그 수 · 실제 갱신률 · 일 증가량)이다. (C)

## 1. 데이터의 종류 — 5계층으로 갈린다

통합 관제에서 다루는 데이터는 성격이 다른 **5개 계층**으로 갈린다.
이 구분이 중요한 이유는 **주기·보관·파이프라인이 계층마다 한 자릿수 이상 다르기 때문**이다.
하나의 정책으로 묶으면 반드시 어딘가가 과설계되거나 데이터가 유실된다.

### 1-1. 로봇·장비 제어 데이터 (Level 1~2)

| 데이터 | 내용 | 주 용도 |
|---|---|---|
| 축별 관절값 | 각 축 위치·속도·가속도 | 궤적 검증, 충돌 분석 |
| 축별 토크·모터 전류 | 서보 부하 | **예지보전의 핵심 신호** — 감속기 그리스 교환·마스터링 시점 판단 (B) |
| 온도 | 모터·컨트롤러·감속기 | 열화·과부하 |
| I/O 상태 | 디지털/아날로그 입출력 | 인터록, 핸드셰이크 |
| 프로그램 컨텍스트 | 실행 중 프로그램·라인 번호·잡 ID | **에러를 공정에 귀속시키는 열쇠** |
| 가동 상태 | run / idle / estop / fault + 정지 사유 | OEE의 가용성 항 |
| 알람·이벤트 | 코드 · 타임스탬프 · 심각도 | 장애 분석 |
| 사이클 카운트·타임 | 개체 수, 소요 | 생산성, 드리프트 감지 |

로봇 유지보수 도구는 컨트롤러에 OPC UA로 붙어 가동 시간과 정지 사유를 추적하고,
**모터 토크를 읽어 그리스 교환·마스터링 시점을 판정**한다. (B)

### 1-2. 공정·설비 데이터 (Level 2)

PLC 태그(압력·유량·온도·위치), CNC 공작기계 데이터, 컨베이어, 지그·픽스처 상태,
바코드/RFID 리더, 토크건 체결값.

**로봇만 보면 안 되는 이유** — 로봇 정지의 상당수는 로봇 고장이 아니라 **주변 설비·자재 공급의
결과**다. 로봇 데이터만 모으면 원인 절에 도달하지 못한다. (C)

### 1-3. 고주파 상태감시 데이터 (별도 취급)

진동, 음향(AE), 모터 전류 파형(MCSA).

1-1과 물리적으로는 같은 대상이지만 **데이터로서는 전혀 다르다.**
샘플링이 kHz 대역이라 SCADA 파이프라인에 그대로 태우면 **대역이 붕괴한다.** (§3 참조)

### 1-4. 품질·추적성 데이터 (Level 3, MES)

제품 단위 genealogy(로트·배치·시리얼), 검사 결과, **비전 판정 및 원본 이미지**,
공정 파라미터 스냅샷, 작업자·교대·설비 배정, 재작업·폐기 이력.

자동차의 경우 **IATF 16949 8.5.2**가 로트·배치·부품 단위 genealogy를 자동 수집·보관하도록
요구한다. (A)

> **비전 이미지는 용량 폭탄이다.** 판정 결과(수 바이트)와 원본 이미지(수 MB)를 같은 보관 정책에
> 넣으면 저장 비용이 통제 불능이 된다. 실무에서는 **NG 및 경계 판정만 원본 보관**이 일반적이다. (C)

### 1-5. 경영·집계 데이터 (Level 3~4)

OEE(가용성 × 성능 × 품질), 생산 실적 대 계획, 에너지 소비(설비별 전력), 재고·자재 소요,
보전 작업 오더(CMMS 연계).

### 1-6. 안전·보안 데이터 (횡단)

안전 PLC 이벤트(라이트커튼 차단, 비상정지, 안전 영역 침범), 협동로봇의 속도·이격 감시 이벤트,
출입 통제, **OT 네트워크 감사 로그**.

마지막 항목은 **IEC 62443 / NIST SP 800-82**가 요구하는 항목이며,
**"관제 데이터"에서 빠뜨리기 가장 쉬운 축**이다. (A · §7 참조)

## 2. 수집 방식 — "OPC UA가 구조를 잡고, MQTT가 나른다"

2026 현재 업계 합의는 명확하다. **OPC UA는 데이터를 구조화하고, MQTT는 그것을 운반한다.**
여기에 **Sparkplug B**를 얹으면 MQTT 메시지에 구조와 일관성이 생겨, 공장 바닥에서 클라우드까지
보안과 데이터 모델을 유지한 채 전달된다. (B)

| 프로토콜 | 위치 | 특징 | 주의점 |
|---|---|---|---|
| **OPC UA** | 장비 ↔ 엣지 | 정보 모델(로트코드·공정 파라미터·설비 ID 등 컨텍스트 포함), 보안 내장 | 폴링 기반이면 소비자마다 부하 증가 |
| **OPC UA PubSub over MQTT** | 엣지 → 상위 | OPC UA 모델 + MQTT 전송 | 비교적 신규, 벤더 지원 편차 |
| **MQTT + Sparkplug B** | 엣지 → 브로커 → N개 소비자 | **상태 관리(birth/death)**, 토픽 네임스페이스·페이로드 스키마 규정 | **브로커가 SPOF — 이중화 필수** |
| **MTConnect** | 공작기계 중심 | 벤더 무관 의미 어휘. ANSI/MTC1.4-2018 | **읽기 전용. 제어 불가** |
| **필드버스** (PROFINET / EtherNet/IP / Modbus TCP) | 제어 계층 | 결정적 실시간 | 관제용 수집에 직접 쓰면 **제어 루프를 방해** |
| **벤더 전용 API** | 장비 직결 | FANUC FOCAS, ABB Robot Web Services, KUKA RSI 등 | 종속. 다른 벤더로 재사용 불가 |
| **ROS 2 / DDS** | 자율이동로봇·연구 계열 | 토픽 기반, 고빈도 | 공장 관제망에 그대로 노출하면 트래픽·보안 문제 |

### 2-1. MTConnect 구조 (공작기계가 섞인 현장이면 필수)

**Adapter**가 장비 컨트롤러에 붙어 신호를 읽고 **SHDR**(파이프 문자 `|` 구분, UTC 타임스탬프로
시작하는 평문 스트림)로 변환해 **Agent**로 흘린다. Agent는 이를 내부 버퍼에 정리하고 HTTP API로
노출한다. Adapter는 장비 위에, Agent는 별도 서버에 두는 것이 일반적이다. (A/B)

### 2-2. 레거시 장비 통합

현장의 현실은 **"20년 된 설비 + 작년에 산 로봇"** 이다.
엣지 게이트웨이가 Modbus·OPC UA를 포함한 **100종 이상의 산업 프로토콜**을 Sparkplug B 규격
MQTT로 번역해 **하드웨어 교체 없이** 편입시킨다. (B)

### 2-3. 설계 원칙 세 가지

1. **폴링을 소비자마다 만들지 않는다.** 장비 → 엣지는 한 번만, 그 뒤는 발행/구독.
   MES·ERP·분석·대시보드가 각자 폴링하면 **장비가 죽는다.** (B)
2. **수집은 읽기 전용 경로로 분리한다.** 관제 수집이 제어 경로에 쓰기 권한을 갖는 순간,
   그것은 관제 시스템이 아니라 **공격 표면**이다. (§7, IEC 62443 zones & conduits)
3. **컨텍스트를 원천에서 붙인다.** 나중에 시간으로 조인해 로트를 맞추는 것은 거의 항상 실패한다.
   OPC UA가 로트코드·설비 ID를 함께 실어주는 것이 이 문제를 푼다. (C)

## 3. 수집 주기 — 계층 간에 4~5자릿수 차이가 난다

**이 표가 이 조사에서 가장 실무적인 부분이다.** 주기를 잘못 잡으면 대역이 터지거나
잡아야 할 이벤트를 놓친다.

| 계층 | 대상 | 주기 / 주파수 | 등급 |
|---|---|---|:---:|
| 로봇 내부 제어 루프 | 서보 제어 | **1 kHz (1 ms)** — KUKA FRI가 내부 제어 계층과 같은 1kHz까지 지원 | B |
| 실시간 외부 제어 IF | KUKA RSI | 4 ms / 12 ms 두 가지 사이클 | B |
| 〃 | ABB EGM, FANUC DPM | 실시간 경로 수정용. RSI와 동급 대역 | B |
| 공정 대량 데이터 수집 | CNC·로봇 | 최소 **100 Hz** (샘플링 주기 ≤ 10 ms) | B |
| 진동 — 베어링·기어 조기 결함 | 상태감시 | **25~50 kHz** 샘플링, 10~20 kHz까지 평탄 응답 권장 | B |
| 진동·전류 (연구 사례) | 유도전동기 PdM | 10 kHz, 1.0초 윈도우 분할 / 다른 사례 50 kHz | B |
| SCADA 태그 폴링 | 압력·온도·상태 | **100 ms ~ 1 s** (일반 관제 기본값) | C |
| 로봇 가동/알람 상태 | 통합 관제 대시보드 | **1 s 또는 변화 시점 이벤트(on-change)** | C |
| MES 이벤트 | 로트 시작/종료, 검사 | **이벤트 기반** (주기 아님) | B |
| OEE·집계 | 대시보드 | 1분 ~ 15분 집계 | C |
| 에너지 | 설비별 전력 | 1분 | C |

**1 kHz에서 15분까지.** 같은 시스템 안에서 6자릿수 차이가 난다.

### 3-1. 실무 결론 세 가지

**① 고주파(kHz)는 절대 중앙으로 원본을 보내지 않는다.**

엣지 게이트웨이가 고속 센서 데이터와 저속 컨트롤러 데이터를 모아 **원본이 아니라
"판단(actionable insight)"** 을 상위로 올린다. (B)
실무 형태는 이렇다 — 엣지에서 FFT/특징량(RMS·크레스트팩터·밴드에너지)을 뽑아 **초당 몇 개 값만**
전송하고, **이상 징후 시에만 원본 파형 버스트를 업로드**한다. (C)

**② 변화 기반(on-change / deadband)이 고정 폴링보다 거의 항상 낫다.**

대부분의 태그는 대부분의 시간 동안 변하지 않는다.
Sparkplug B의 상태 관리가 이것을 **안전하게** 만든다 — 값이 안 오는 것이 *"정상 무변화"* 인지
*"죽음"* 인지 구분해 주기 때문이다. (C)

**③ 주기는 "용도"가 정하지 "가능한 최대"가 정하지 않는다.**

1 ms로 뽑을 수 있다는 것과 1 ms로 저장해야 한다는 것은 다른 문제다.

> 측정점 **5,000개**를 **1초 주기**로만 받아도 **하루 4억 3,200만 레코드**다. (B)

## 4. 보관 주기 — 이건 기술 결정이 아니라 규제 결정이다

엔지니어가 정하는 것은 **"언제 계층을 옮기나"** 이고,
**"언제 지워도 되나"** 는 법규와 고객 요구(CSR)가 정한다.

### 4-1. 기술적 계층(tier) — 일반 관행

| 계층 | 매체 | 보관 대상 | 통상 기간 | 등급 |
|---|---|---|---|:---:|
| **Hot** | 메모리 · NVMe SSD | 최근 센서값, 활성 알람, 현재 공정 제어 데이터 | 센서 24시간 / 품질 7일 | B |
| **Warm** | 일반 디스크 | 트렌드 요약 — AI 예측 모델 학습용 | 1~5년 (센서 원본은 30일 후 이동 사례) | B |
| **Cold** | 아카이브 · 오브젝트 스토리지 | 규제 대응 | 5~10년 | B |

품질 데이터의 예시 정책 — **hot 7일 / warm 90일 / cold 7년.** (B)

### 4-2. 규제가 강제하는 하한

| 영역 | 근거 | 요구 보관 | 등급 |
|---|---|---|:---:|
| **자동차** | IATF 16949 7.5.3.2.1 · 8.5.2 | 통상 **10~15년**. PPAP·금형·설계·계약은 **N+1 역년**(N=생산/서비스 수명). 안전 핵심 특성은 OEM CSR이 더 길게 요구 | A |
| **제약·바이오 (GxP)** | FDA 21 CFR Part 11 · EU GMP Annex 11 · PIC/S PI 041 | 전자기록·감사추적을 레코드 보관 기간 **내내 재현 가능하게**. 감사추적은 **who/what/when/why** 전부 | A |
| **식품** | FDA FSMA 204 | KDE(핵심데이터요소) **최소 2년**. FDA 요청 시 **24시간 내 제출** | A |
| **석유·가스** | FERC · PHMSA | 공정 데이터 **최소 7년**. 실무상 20~30년 보관 운영사 다수 | B |
| **산업안전 (미국)** | OSHA | 유해인자 노출 기록은 **퇴직 후 30년**. 교육·정비 결함 로그는 3년 이상 | A |
| **반도체** | 고객사(팹) 요구 · SEMI | 표준 자체는 연한을 못박지 않음. **고객 계약이 정한다** | C |

### 4-3. 설계 시 실수하기 쉬운 지점

- **"평균 7년"으로 뭉뚱그리면 반드시 비용이 터진다.**
  1 kHz 원본을 7년 두는 것과 1분 집계를 7년 두는 것은 **수천 배 차이**다.
  **해상도별로 다른 기간**을 걸어야 한다. (C)
- **감사추적(audit trail)은 데이터보다 오래 산다.**
  GxP 영역에서는 값 자체보다 *"누가 언제 왜 바꿨는가"* 의 보관이 더 엄격하다. (A)
- **삭제도 정책이다.** EU GDPR이 걸리는 작업자 식별 데이터(작업자 ID·생체·위치)는
  **보관 상한**이 있다. **"다 남긴다"가 준법이 아니다.** (C)

## 5. 데이터 파이프라인

### 5-1. Unified Namespace (UNS)

브로커를 **"현재 공장 상태의 단일 진실 원천"** 으로 두고, 모든 시스템이 점대점 연결 대신
브로커를 향하게 하는 구성.

효과는 **폴링 부하 제거 + 소비자별 개별 연동 소멸**이다. CNC·로봇팔·컨베이어의 텔레메트리를
MQTT로 MES/ERP에 실시간 반영하되, 폴링 오버헤드도 소비자마다의 점대점 연동도 없다. (B)

United Manufacturing Hub 같은 오픈소스 스택은 **TimescaleDB + UNS(MQTT/Kafka)** 조합을
제품화했다. (B)

### 5-2. 브로커 vs 스트림 — 둘 다 필요한가

| | MQTT 브로커 | Kafka |
|---|---|---|
| 역할 | 현재 상태 전파, 경량, OT 친화 | **재생 가능한 로그**, 대용량 버퍼, 백프레셔 |
| 필요해지는 시점 | **처음부터** | 소비자가 늘고 **재처리·리플레이**가 필요해질 때 |

소규모 현장에서 Kafka를 처음부터 넣는 것은 **과설계일 가능성이 높다.** (C)
**MQTT + TSDB로 시작**해서, *"과거 데이터를 다시 흘려 모델을 재학습해야 한다"* 는 요구가
**실제로 생겼을 때** Kafka를 넣는 순서를 권한다. (C)

### 5-3. 히스토리안 / TSDB 선택지

| | 성격 |
|---|---|
| **AVEVA PI System** | 전통 히스토리안. OT 통합·장기 운영 실적. 라이선스 비용 큼 |
| **InfluxDB** | 시계열 특화. 압축비 **10:1** 수준. 윈도우 집계·다운샘플링·미분·추세 내장. 2.x는 고카디널리티 태그에 제약(3.0 컬럼너로 완화) |
| **TimescaleDB** | PostgreSQL 확장. 무손실 압축률 **94~97%**. 연속 집계(continuous aggregates) = 변경된 청크만 증분 갱신하는 머터리얼라이즈드 뷰 |

**PostgreSQL을 이미 쓰는 팀이면 TimescaleDB가 학습 비용이 가장 낮다.** (C)

## 6. 보관 및 처리 방식

### 6-1. 규모 감각 먼저

> 측정점 **5,000개** × **1초 샘플링** = 하루 **4억 3,200만 레코드**. (B)

이 숫자가 아래 모든 기법의 존재 이유다.
시계열 최적화 저장 · 컬럼너 압축 · 시간 파티셔닝 질의 실행이 없으면 성립하지 않는다.

### 6-2. 적용 기법

| 기법 | 내용 | 효과 |
|---|---|---|
| **엣지 선별** | 고주파 원본을 올리지 않고 특징량만 전송, 이상 시에만 원본 버스트 | 대역·저장 **수십~수백 배** 절감 (C) |
| **데드밴드 / on-change** | 변화 폭이 임계 미만이면 기록하지 않음 | 무변화 태그 비용 제거 (C) |
| **컬럼너 압축** | TimescaleDB 94~97% 무손실 / InfluxDB ~10:1 | 저장 비용 (B) |
| **연속 집계 · 다운샘플링** | 원본 1초 → 1분/1시간/1일 롤업을 증분 유지 | 대시보드 질의 속도 (B) |
| **해상도별 차등 보관** | 원본 30일 · 1분 집계 2년 · 1시간 집계 10년 | 규제 준수와 비용의 양립 (C) |
| **시간 파티셔닝** | 청크 단위 분할 | 오래된 파티션 통째 아카이브·삭제 (B) |
| **자동 티어 이동** | 나이 임계값 기반 hot→warm→cold | 운영 부담 제거 (B) |

### 6-3. 반드시 결정해야 하는 4가지

1. **타임스탬프의 출처.** 장비 시계인가 게이트웨이 시계인가.
   NTP/PTP 동기화가 없으면 여러 설비의 데이터를 조인하는 순간 **인과관계가 뒤집힌다.**
   **이게 가장 흔한 사고다.** (C)
2. **결측과 "값이 안 온 것"의 구분.** Sparkplug B의 birth/death가 이 문제를 다룬다. (B)
3. **원본 불변성.** GxP 영역에서는 **원본을 덮어쓰는 다운샘플링이 곧 위반**이다.
   집계는 **파생 테이블**로 만들고 원본은 손대지 않는다. (A — ALCOA+의 *Original*)
4. **스키마 진화.** 설비 교체·태그 추가는 반드시 일어난다.
   Sparkplug B의 토픽 네임스페이스와 ISA-95 계층을 미리 정해두지 않으면
   **3년 뒤 태그 이름이 난장판**이 된다. (C)

## 7. 표준 · 보안 규정 · 법규

세 종류를 구분한다 — ① **구조 표준**(어떻게 쌓을지) · ② **보안 규정**(어떻게 지킬지) ·
③ **법규**(안 지키면 처벌·시장 진입 불가).

### 7-1. 구조 표준

| 표준 | 내용 | 왜 중요한가 |
|---|---|---|
| **ISA-95 / IEC 62264** | 제조 운영 계층(Level 0~4)과 표준 용어 체계 | 통합 관제의 계층 구분이 여기서 나온다. IEC 62443의 zones & conduits가 이 모델 위에 세워졌다 (A) |
| **Purdue 모델** | ICS 계층 참조 모델 | IEC 62443 · NIST SP 800-82와 정렬. 규제 산업에서 준수 근거로 통용 (A/B) |
| **ISA-88 / IEC 61512** | 배치 공정 제어 모델 | 화학·제약 배치 현장 |
| **MTConnect** (ANSI/MTC1.4-2018) | 제조 장비용 의미 어휘 | 벤더 종속 없는 태그 명명 (A) |
| **OPC UA** (IEC 62541) | 정보 모델 + 보안 통신 | **사실상의 통합 관제 기본 규격** (A) |
| **Sparkplug B** | MQTT 토픽 네임스페이스·페이로드 스키마·상태 관리 | **MQTT를 OT에서 쓸 수 있게 만드는 것** (B) |

### 7-2. 보안 규정

| 규정 | 요구 사항 | 관제 설계에 주는 제약 |
|---|---|---|
| **IEC 62443** | **Zones & Conduits** — 보안 요구가 비슷한 자산을 zone으로 묶고, zone 간 데이터 이동은 conduit로 통제 | **데이터 수집 경로가 곧 conduit다.** 수집기를 아무 데나 두면 그 자체가 위반 (A) |
| **NIST SP 800-82** | Purdue + 62443 zones/conduits 파생 계층 참조 모델로 OT망 구성 | 미국·글로벌 제조 실무 표준 (A) |
| **공통 — 로깅·감사추적** | 두 프레임워크 모두 로깅·감사추적·보안 이벤트 탐지 능력 요구 | OT에서는 **수동(passive) 네트워크 모니터링**으로 해야 한다 — 결정적 제어 루프를 방해하는 **능동 트래픽 주입 금지** (A) |
| **EU NIS2** | 필수·중요 주체의 사이버보안 관리·사고 보고 | 제조업 상당수가 대상. 로그 보관·보고 체계 필요 (B) |

> **설계에 즉시 반영해야 할 한 줄** — 관제용 데이터 수집은
> **수동 · 읽기전용 · 단방향(데이터 다이오드 지향)** 으로 설계한다.
> 관제 편의를 위해 상위망에서 제어망으로 쓰기 경로를 여는 순간 62443 구조가 무너진다. (C)

### 7-4. ALCOA+ — 규제 산업이 아니어도 쓸 만한 원칙

**A**ttributable(귀속 가능) · **L**egible(판독 가능) · **C**ontemporaneous(동시 기록) ·
**O**riginal(원본) · **A**ccurate(정확) **+** Complete · Consistent · Enduring · Available. (A)

타임스탬프·다운샘플링 문제와 **정확히 같은 이야기**다. (C)

## 8. 정리 — 설계 착수 시 결정 순서

조사 결과를 실행 순서로 압축하면 **8단계**다.
**순서가 중요하다** — 뒤 항목이 앞 항목의 답을 전제로 하기 때문이다.

| # | 결정 | 잘못하면 |
|:---:|---|---|
| 1 | **어느 규제가 걸리는가** (산업·수출 지역) | 보관 기간과 감사추적 요구가 전부 바뀐다. **나중에 바꾸면 재구축** |
| 2 | **데이터 계층 5분류** 중 무엇을 다루는가 | 하나의 정책으로 묶어 과설계 또는 유실 |
| 3 | **계층별 주기** — 특히 kHz 대역을 엣지에서 끊을 것 | 대역 붕괴 |
| 4 | **네임스페이스 설계** — ISA-95 계층 + Sparkplug B 토픽 규칙 | 3년 뒤 태그 난장판 |
| 5 | **시간 동기화** — NTP/PTP | 인과관계 역전. 조인 불가 |
| 6 | **62443 zones & conduits 상 수집기 배치** (읽기전용·단방향) | 관제 시스템이 공격 표면이 됨 |
| 7 | **해상도별 차등 보관 정책** (원본/집계 각각) | 저장 비용 폭발 또는 규제 위반 |
| 8 | **데이터 반출 API** (EU Data Act 대응) | 2025-09-12 이후 EU 시장에서 법적 문제 |

## 이 조사에서 확인하지 못한 것

정직하게 남긴다.

- 한국 **산업안전보건법·중대재해처벌법**의 로봇 관련 데이터 보관 조문 — 조문 원문 미확인 (C로 남김)
- **EU 기계류 규정 2023/1230** 및 **AI Act**의 구체적 데이터 조항 — 적용 여부 판단 필요
- **ISO 10218 / ISO/TS 15066**(로봇·협동로봇 안전)의 기록 요구 사항 — 이번 조사 범위 밖
- **실제 현장 태그 수·일 증가량** — 문헌으로는 알 수 없다. **실측 필요**
