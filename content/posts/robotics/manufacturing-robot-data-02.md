[1편](../제조-로봇-통합관제-데이터-01-종류-주기-보관-법규/)에서는 통합 관제가 다루는 데이터의 종류·주기·보관·법규를
정리했다. 프로토콜은 표 한 장으로 압축했는데, 그 표는 **선택지를 나열할 뿐 왜 둘을 같이 쓰는지는
말하지 않는다.**

이 글이 그 배경이다. **OPC UA · MQTT · Sparkplug B** 세 가지가 어떻게 맞물리는지, 그리고
**어디서 사람들이 자빠지는지**를 다룬다.

검증 등급(A/B/C) 규약은 1편 §0을 그대로 승계한다.

| 등급 | 의미 |
|:---:|---|
| **A** | 표준 문서 · 법령 원문 · 규제기관 문서에 명시된 사실 |
| **B** | 복수의 벤더/업계 문서가 일치하는 통용 수치 |
| **C** | 단일 출처 또는 내 추론. 그대로 설계 근거로 쓰지 말 것 |

---

## 1. 왜 둘인가 — 한 장 요약

두 프로토콜은 **경쟁 관계가 아니다. 층이 다르다.**

| | **OPC UA** | **MQTT** |
|---|---|---|
| 표준 | IEC 62541 (A) | OASIS 표준. 3.1.1은 ISO/IEC 20922:2016 (A) |
| 답하는 질문 | *"이 값이 **무엇**인가"* | *"이 값을 **어떻게 여러 곳에** 보내는가"* |
| 잘하는 것 | 의미 · 구조 · 보안 | 분배 · 확장 · 저대역 |
| 못하는 것 | 다수 소비자에 무겁다, 방화벽 통과가 껄끄럽다 | **의미가 없다** — 페이로드가 완전 자유 |
| 자리 | 장비 ↔ 엣지 | 엣지 → 브로커 → N개 소비자 |

한 줄로:

> **OPC UA는 값에 의미를 붙이고, MQTT는 그것을 싸게 많이 나르며,
> Sparkplug B는 MQTT 쪽에 일관된 네임스페이스·스키마·상태 관리를 부여한다.** (C)

> ⚠️ **Sparkplug가 OPC UA의 정보 모델을 복원해 주는 것은 아니다.**
> 참조 트리 · 컴패니언 스펙 의미 · browse 가능한 주소공간은 **자동으로 넘어오지 않는다.**
> 두 모델 사이의 매핑은 **별도 설계 항목**이며, 이걸 빼먹으면 **엣지에서 의미가 소실된다.** (C)

## 2. OPC UA ① — 핵심은 프로토콜이 아니라 정보 모델

### 2-1. 태그 목록이 아니라 트리다

보통의 산업 프로토콜은 **값만** 준다.

OPC UA는 **주소공간(address space)** 이라는 트리를 노출한다.
값 옆에 **자료형 · 단위 · 유효범위 · 타임스탬프 · 품질코드**가 붙고, 노드끼리 **참조(reference)** 로
묶인다.

이 "참조"가 결정적이다. **나중에 타임스탬프로 조인해 로트를 맞추는 방식은 거의 항상 깨진다.**
OPC UA는 컨텍스트를 **원천에서 값에 붙여** 그 문제를 없앤다. (C — 이 판단은 내 추론이다)

### 2-2. 컴패니언 스펙 — 벤더가 달라도 이름이 같아지는 이유

정보 모델은 **업종별로 미리 표준화**된다.
로봇은 VDMA와 OPC Foundation의 공동 작업인 **OPC UA for Robotics** 계열이 있고,
공작기계는 **umati** 계열이 있다. (B)

**실무 함의** — 컴패니언 스펙을 지원하는 장비를 고르면 통합 비용이 크게 줄어든다.
지원하지 않으면 **벤더별 태그 매핑표를 사람이 만들어야 하고, 그 매핑표가 곧 부채가 된다.** (C)

### 2-3. 서비스와 구독 메커니즘

Client/Server 모드에서 클라이언트는 **폴링하지 않고 Subscription을 만든다.**
여기 붙는 파라미터가 대역과 부하를 결정한다. (A)

| 파라미터 | 뜻 | 실무 감각 |
|---|---|---|
| **Sampling interval** | 서버가 값을 들여다보는 주기 | 장비 능력이 하한을 정한다 |
| **Publishing interval** | 모아서 보내는 주기 | 샘플링보다 크게 잡아 묶어 보낸다 |
| **Deadband** | 이 변화폭 미만은 안 보냄 | **대역 절감의 핵심 손잡이** |
| **Queue size** | 발행 사이에 쌓는 버퍼 | 넘치면 유실(또는 최신값 덮어쓰기) |

**핵심** — 값이 안 바뀌면 데이터 변경 알림이 나가지 않는다. **폴링과 근본적으로 다른 지점이다.** (A)

> ⚠️ **"트래픽이 0이 된다"는 아니다.** Subscription은 알릴 것이 없어도 **KeepAlive**를 보내
> 연결이 살아 있음을 알린다. 대역 산정에서 이 몫을 빼먹으면 안 된다. (A)

## 3. OPC UA ② — Client/Server vs PubSub, 그리고 보안

### 3-1. 두 가지 통신 모델

**이 구분이 실무에서 가장 자주 헷갈린다.**

| | **Client/Server** | **PubSub** (IEC 62541-14) |
|---|---|---|
| 연결 | 세션 기반 **1:1**. `opc.tcp://`, 기본 포트 **4840** | 세션 없음. 발행자 → 다수 |
| 데이터 | Subscription + MonitoredItem | **DataSet**을 주기 발행 |
| 전송 | TCP 직결 | **메시지 매핑**(UADP 또는 JSON) × **전송 매핑**(UDP·이더넷·MQTT·AMQP)의 조합 |
| 성격 | 확실하지만 무겁다. 소비자가 늘면 서버 부하가 는다 | 가볍고 다수 소비자에 유리 |
| 주의 | NAT·방화벽 통과가 껄끄럽다 | 비교적 신규 — **벤더 지원 편차** (B) |

IEC 62541-14는 **PubSub이 Client/Server를 대체하는 것이 아니라 보완한다**고 명시한다 —
장치 네트워크 안뿐 아니라 IT·분석 클라우드까지 데이터를 배포하기 위한 모델이다. (A)

**메시지 인코딩과 전송을 따로 고르는 구조**라는 점이 중요하다.
**"MQTT면 JSON"이 아니다** — UADP를 MQTT로 나르는 구성도 성립한다. (B)
그래서 **"OPC UA PubSub over MQTT"** 라는 조합이 나온다.

> 다만 이것이 옮기는 것은 **발행하도록 구성한 DataSet**이지 **서버의 주소공간 전체가 아니다.**
> browse 가능한 정보 모델을 그대로 옮겨주는 것으로 오해하면 안 된다. (C)

### 3-2. 보안이 표준 안에 있다

OPC UA는 **보안이 스펙 레벨**이다 — X.509 인증서 기반 상호 인증, 메시지 서명·암호화,
사용자 인증이 **프로토콜에 포함**된다. (A)

**MQTT에는 이것이 없다.** MQTT의 보안은 TLS로 감싸고 브로커에서 인증·인가를 거는 **별도 층**이다. (A)

→ **설계 함의**: **엣지에서 MQTT로 넘어가는 순간 보안 모델이 바뀐다.**
그 경계에서 인증 체계를 이어붙이는 것이 설계자의 몫이다. (C)

### 3-3. 이 프로토콜은 쓰기도 된다 — 관제에서 가장 위험한 지점

OPC UA는 **원래 읽기 전용이 아니다.** 메서드 호출과 쓰기가 규격에 있다. (A)

따라서 **관제 수집용 계정은 반드시 읽기 전용으로 분리**해야 한다.

> 수집 경로가 제어 경로에 쓰기 권한을 갖는 순간,
> **그것은 관제 시스템이 아니라 공격 표면이다.** (B)

1편 §7의 IEC 62443 zones & conduits와 같은 이야기다.

## 4. MQTT — 많은 곳으로 싸게 나르는 쪽

### 4-1. 표준 지위부터 정확히

- **MQTT 5.0은 OASIS 표준**이다. (A)
- **ISO/IEC 20922:2016은 3.1.1이다. 5.0이 아니다.** (A)
  → 사양서에 *"ISO 표준 MQTT 5.0"* 이라고 쓰면 **틀린 문장**이 된다. 자주 나오는 혼동이다.
- 기본 포트: 평문 **1883**, TLS **8883**. (B)

### 4-2. 구조 — 발행자와 구독자는 서로를 모른다

브로커 하나에 발행자·구독자가 붙는다.
이것이 1편 §2-3 *"폴링을 소비자마다 만들지 않는다"* 의 구현체다.

> **장비는 한 번만 읽히고, 소비자가 4개든 40개든 장비 부하는 그대로다.** (B)

### 4-3. 실제로 쓰는 기능들

왼쪽은 **규격이 정하는 것**, 오른쪽은 **실무 판단**이다. 등급을 칸별로 나눠 붙인다.

| 기능 | 규격이 정하는 것 | 왜 중요한가 (실무 판단) |
|---|---|---|
| **QoS 0/1/2** | 0 = 최대 1회(유실 가능), 1 = 최소 1회(중복 가능), 2 = 정확히 1회 (A) | 현장 텔레메트리는 대개 **1**. 2는 왕복이 늘어 느리다 (B) |
| **Retained message** | 토픽의 마지막 값을 브로커가 보관했다가 새 구독자에게 전달 (A) | 대시보드가 켜지자마자 빈 화면이 아닌 이유 (C) |
| **LWT (Last Will)** | 클라이언트가 비정상 종료하면 **브로커가 대신** 지정 메시지를 발행 (A) | **Sparkplug 죽음 통보의 토대** (B) |
| **Persistent session** | 재접속 시 구독과 미전달 QoS 메시지를 유지 (A) | 끊김이 잦은 현장일수록 값을 한다 (C) |
| **와일드카드** | `+` 한 레벨, `#` 나머지 전부 (A) | `factory/+/robot/#` 같은 소비자 분리에 쓴다 (C) |
| **MQTT 5.0 추가분** | shared subscription, message expiry, user properties, topic alias, reason code (A) | **소비자 스케일아웃이 5.0에서 훨씬 쉬워진다** (B) |

### 4-4. 그리고 결정적 약점

**MQTT는 페이로드에 아무 규칙이 없다.** 토픽 이름도 자유, 내용도 자유다. (A)

> 팀 셋이 붙으면 **토픽 체계가 셋 생긴다.**
> OPC UA가 애써 붙인 의미가 MQTT로 넘어오는 순간 **증발한다.** (C)

## 5. Sparkplug B — 증발한 의미를 되살린다

§4-4의 구멍을 메우는 것이 **Eclipse Sparkplug**다. MQTT 위에 얹는 규격이며,
**3.0.0부터 Eclipse Foundation의 정식 사양 프로세스**로 관리된다. (A)

### 5-1. 무엇을 규정하는가

- **토픽 네임스페이스** — 첫 토큰은 `spBv1.0`(또는 `spAv1.0`)로 고정되며,
  **이 토큰이 페이로드 인코딩을 뜻한다.** (A)

  ```text
  spBv1.0/{Group ID}/{message_type}/{Edge Node ID}/[{Device ID}]
  ```

- **페이로드** — 자유 JSON이 아니라 **protobuf로 규정**된다. (B)
- **상태 관리** — 아래가 핵심이다.

### 5-2. Birth / Death — "값이 안 온다"와 "장비가 죽었다"를 구분한다

| 메시지 | 뜻 |
|---|---|
| `NBIRTH` / `DBIRTH` | **출생 신고.** 전체 태그 목록과 현재값을 한 번에 선언 |
| `NDATA` / `DDATA` | 이후의 **변경분만** 전송 |
| `NDEATH` / `DDEATH` | **사망 신고** |
| `NCMD` / `DCMD` | 하향 명령 |
| `STATE` | 주 애플리케이션(Primary Host)의 상태 |

사양은 엣지 노드가 **접속 후 다른 어떤 메시지보다 먼저 `NBIRTH`를 발행**해야 하고,
`{namespace}/{Group ID}/NDEATH/{Edge Node ID}` 를 **MQTT Will 토픽으로 등록**해야 한다고
규정한다. (A)

**왜 이것이 결정적인가**

- `NBIRTH`를 받은 소비자는 이후의 **변경분(`NDATA`)만으로 전체 상태를 재구성**할 수 있다.
  태그 목록을 별도 문서로 주고받을 필요가 없다.
- `NDEATH` 덕분에 ***"값이 안 오는 것"*** 과 ***"장비가 죽은 것"*** 을 **구분할 수 있다.**
  이 구분이 없으면 **관제 화면이 조용히 거짓말을 한다** — 마지막 값이 그대로 떠 있는데
  그게 현재값인지 유물인지 알 수 없다. (C)

> ⚠️ **늦게 붙은 소비자는 그냥 되지 않는다.**
>
> `NBIRTH`는 **한 번 발행되고 지나간 메시지**다. 그 뒤에 접속한 소비자는 과거 `NBIRTH`를
> 자동으로 받지 못한다. **MQTT의 retained message와 같은 효과로 오해하면 안 된다.**
>
> 상태를 맞추려면 **rebirth 요청(`NCMD`)** 같은 동기화 절차를 같이 설계해야 하고,
> Primary Host의 `STATE` 흐름도 함께 봐야 한다. (B)
>
> **Sparkplug 도입 실패의 흔한 원인이 여기다** — 붙는 순서를 고려하지 않은 소비자가
> **빈 상태로 돌기 시작한다.** (C)

(내가 반대 방향에서 같은 함정에 빠진 기록은
[관제 화면의 회색 점이 몇 초 만에 켜지는지 나는 틀리게 기억하고 있었다](../관제화면-회색점-3초-heartbeat-vs-sparkplug/)에 있다.)

### 5-3. 부수 장치

- **시퀀스 번호(`seq`)** — 메시지 유실·순서 이상을 소비자가 감지한다 (B)
- **alias** — 긴 태그 이름을 숫자로 치환해 대역을 아낀다 (B)

## 6. 조합 아키텍처와 설계 원칙

### 6-1. 엣지 게이트웨이가 번역기이자 경계다

레거시 설비(Modbus 등)와 최신 로봇(OPC UA)이 섞인 현장에서, 엣지 게이트웨이가
여러 산업 프로토콜을 **Sparkplug 규격 MQTT로 번역**해 하드웨어 교체 없이 편입시킨다. (B)

엣지는 번역만 하는 곳이 아니라 **세 가지가 동시에 일어나는 경계**다 (C):

1. **프로토콜 번역** (OPC UA / Modbus → MQTT)
2. **보안 모델 전환** (OPC UA 내장 보안 → TLS + 브로커 인가)
3. **감축** (deadband · 집계로 상위 대역을 줄인다)

### 6-2. 자주 밟는 지뢰

| 지뢰 | 증상 | 대응 |
|---|---|---|
| **브로커 SPOF** | 브로커 하나 죽으면 **공장 전체 가시성이 사라진다** | 클러스터·이중화 (B) |
| **재연결 폭풍** | 네트워크 복구 순간 **전 노드가 동시에 재접속·재발행** | Sparkplug birth가 무겁다면 분산 백오프 (C) |
| **소비자마다 폴링** | 장비가 죽는다 | 장비→엣지는 한 번만, 그 뒤는 발행/구독 (B) |
| **수집 계정에 쓰기 권한** | 관제가 공격 표면이 된다 | 읽기 전용 분리 (§3-3) (B) |
| **시계 불일치** | 이벤트 순서가 뒤집혀 **원인 분석이 불가능해진다** | 엣지에서 NTP·타임스탬프 정책 통일 (C) |
| **토픽 체계 난립** | 팀마다 다른 이름. **나중에 못 고친다** | Sparkplug 또는 사내 UNS 규약을 **먼저** 고정 (C) |

### 6-3. 결정 순서

1. **정보 모델을 먼저 정한다** — 태그 이름·단위·컨텍스트. **프로토콜 선택보다 앞이다**
2. **토픽 네임스페이스를 고정한다** — Sparkplug를 쓸지, 사내 UNS 규약을 쓸지
3. **QoS · deadband · 발행 주기를 대역 예산에서 역산한다** (1편 §3)
4. **그 다음에** 브로커·게이트웨이 제품을 고른다

> 역순으로 하면 **제품이 데이터 모델을 결정하게 된다. 그것이 가장 비싼 실수다.** (C)

## 7. 웨어러블/행동 데이터를 여기에 얹을 때 — 안 맞는 지점

작업자 행동 데이터(스마트 장갑·HMD·IMU 밴드)는 이 파이프라인에 **그대로 들어오지 않는다.**

- **웨어러블은 OPC UA를 말하지 않는다.** 대개 **BLE → 벤더 게이트웨이 → 벤더 클라우드(REST)** 로
  나간다. → 벤더 클라우드에서 빼내 MQTT로 재발행하는 **어댑터 구간이 하나 더** 필요하다.
  기계 데이터에는 없던 구간이고, **여기가 이 통합의 실제 비용**이다. (C)
- **작업단위 라벨은 이벤트다.** OPC UA의 주기 샘플링 모델에 잘 안 맞는다.
  MQTT 쪽이 자연스럽지만, Sparkplug의 birth/death도 **사람에게는 의미가 다르다** —
  작업자가 장갑을 벗은 것은 "장비 고장"이 아니다. **죽음 신고를 그대로 알람에 걸면 오경보가 난다.** (C)
- ⛔ **개인 식별자를 토픽 경로에 박지 마라.**
  `spBv1.0/{Group ID}/.../{Edge Node ID}/{Device ID}` 구조에 **사번이 들어가면
  브로커·히스토리안·백업 전체에 퍼지고 되돌릴 수 없다.** 익명 ID 매핑은 **엣지 경계에서 끊는다.** (C)
- **보관 상한이 다르다.** 기계 데이터는 **저장 비용**이 기준이지만 사람 데이터는 **법**이 상한을 정한다.
  같은 토픽 트리에 담으면 보관 정책을 분리할 수 없다. (C)

> **결론** — 행동 데이터를 이 파이프라인에 얹는 것은 **가능하지만**,
> **어댑터 · 익명화 경계 · 별도 보관 정책** 세 가지를 추가로 설계해야 한다.
> *"MQTT니까 그냥 얹으면 된다"* 는 성립하지 않는다. (C)
