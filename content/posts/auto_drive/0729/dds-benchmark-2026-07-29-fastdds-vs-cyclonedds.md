# ROS 2 로봇 CPU 부하 튜닝 — 미들웨어 교체와 중복 노드 제거

**실측일** 2026-07-29 · **대상** 자율주행 로봇 3대 — **RPi4**(로봇44·50) / **RPi5**(로봇31), 각 4코어 aarch64 · **ROS 2 Jazzy**

4코어 라즈베리파이에서 Nav2 스택이 **정지 상태에서도 CPU의 60% 이상**을 소비하는 문제를 실측으로 추적했다.
두 가지 레버를 각각 A/B 측정으로 검증했다.

| # | 튜닝 포인트 | 결과 | 위험 |
|---|---|---|---|
| **①** | **미들웨어 교체** Fast DDS → Cyclone DDS | 순찰 구간 **−34.19%p**(−12.6%) | 중 — 전 노드 동시 전환 필요 |
| **②** | **중복 `joint_state_publisher` 제거** | **−19.01%p**, 실기 검증 완료 | **없음** |

그리고 측정 과정에서 두 가지가 더 드러났다.

- **진짜 병목은 카메라**(AprilTag detector) — 단독 **87.91%**
- ★**3번째 로봇(31)으로 교차검증하니, 절대 수치는 하드웨어 세대에 좌우됐다.**
  원인은 **보드 세대**였다 — 로봇44·50은 **RPi4**, 로봇31은 **RPi5**. 같은 코드가 RPi5에서는 CPU **4분의 1**로 돈다(§9-B).
- ★**그러나 4번째 로봇(87, RPi4)이 도킹을 완주하면서 "보드 교체가 답"이라는 결론은 철회했다.**
  임계는 보드가 아니라 **CPU 여유** — RPi4라도 도킹 중 idle 20%가 남으면 완주한다(§9-C).

- ①은 §1~§8, ②는 **§9-A**, 교차검증은 **§9-B**, **4번째 로봇으로 한 재정정은 §9-C**, 종합 판단은 **§9-C-4**에 있다.

## 1. 배경 — ROS 2에서 DDS란 무엇인가

### 1-1. ROS 1과 결정적으로 다른 점

ROS 1은 중앙 `roscore`(마스터)가 노드들을 중개했다. 마스터가 죽으면 전체가 멈추고, 실시간성·보안 보장이 없었다.
**ROS 2는 마스터를 없애고 그 자리에 산업 표준 통신 미들웨어인 DDS(Data Distribution Service)를 넣었다.**

```
[ROS 1]  노드 ──▶ roscore(마스터) ──▶ 노드        중앙 집중, 단일 실패점
[ROS 2]  노드 ◀──▶ DDS 분산 디스커버리 ◀──▶ 노드   마스터 없음, P2P
```

DDS는 OMG(Object Management Group)가 표준화한 **발행-구독 미들웨어**로,
항공·국방·금융 등에서 쓰이던 기술이다. ROS 2는 이를 `rmw`(ROS MiddleWare) 추상 계층으로 감쌌다.

### 1-2. 계층 구조

```
 애플리케이션        내 노드 (rclpy / rclcpp)
 ─────────────────────────────────────────────
 클라이언트 라이브러리   rcl (C 공통 구현)
 ─────────────────────────────────────────────
 ★ 추상 계층          rmw  ← 여기서 DDS 구현체를 갈아 끼운다
 ─────────────────────────────────────────────
 DDS 구현체          Fast DDS │ Cyclone DDS │ Connext │ …
 ─────────────────────────────────────────────
 전송                UDP / TCP / 공유메모리
```

**`RMW_IMPLEMENTATION` 환경변수 하나로 구현체를 교체할 수 있다.** 애플리케이션 코드는 한 줄도 바뀌지 않는다.
이것이 이 실험이 성립하는 이유다.

### 1-3. DDS가 실제로 하는 일

| 기능 | 설명 | 로봇에서의 의미 |
|---|---|---|
| **디스커버리** | 노드들이 서로를 자동으로 찾음(SPDP/SEDP) | `roscore` 없이 로봇·PC 노드가 자동 연결 |
| **QoS** | 신뢰성·내구성·이력 등 22종 정책 | 센서는 유실 허용(BEST_EFFORT), 맵은 늦게 붙어도 수신(TRANSIENT_LOCAL) |
| **도메인 격리** | `ROS_DOMAIN_ID`로 논리 분리 | 로봇마다 도메인을 나눠 다중 로봇 운용 |
| **직렬화·전송** | CDR 직렬화 + UDP 멀티캐스트/유니캐스트 | 대역폭·지연·CPU 비용이 여기서 발생 |

### 1-4. 주요 구현체 비교

| | **Fast DDS** (eProsima) | **Cyclone DDS** (Eclipse) |
|---|---|---|
| ROS 2 Jazzy | **기본값** | 선택 설치 |
| 특징 | 기능 풍부(공유메모리, 디스커버리 서버, XML 프로파일) | 경량·단순, 코드베이스가 작음 |
| 설정 | XML 프로파일 + `ROS_STATIC_PEERS` | `CYCLONEDDS_URI` XML |
| 평판 | 기능성 | **자원 효율** — 이 실험의 가설 |

### 1-5. 왜 이 실험을 했는가

측정 대상 로봇의 상시 부하가 비정상적으로 높았다.

- **정지 상태에서도** Nav2·측위·base 프로세스 합계가 **단일 코어 기준 243%**(4코어의 61%)
- 임무(순찰·도킹)가 추가로 쓰는 건 **+10~27%p뿐** — 즉 **부하의 본체는 "스택이 떠 있다는 사실 자체"**
- 정지 중인데도 노드마다 **초당 150~185회 컨텍스트 스위치** → 계산이 아니라 **통신 대기·깨어남 비용**

이 구조라면 미들웨어 교체가 유효한 레버가 될 수 있다는 가설을 세우고 A/B 측정을 설계했다.

## 2. 측정 방법

| 항목 | 내용 |
|---|---|
| 대상 | 로봇 1대(동일 하드웨어·동일 코드), **Raspberry Pi 4 Model B** / 4코어 / 3,784 MiB · 최대 1.8GHz |
| 미들웨어 | A = `rmw_fastrtps_cpp`(기본) · B = `rmw_cyclonedds_cpp` 2.2.3 |
| 조건 | ① 정지(임무 없음) ② 순찰 주행 중 ③ 도킹+카메라(AprilTag 검출) |
| 표본 | 조건당 **60초**(도킹만 40초), 1초 간격 |
| 도구 | `mpstat -P ALL`(시스템), `pidstat -u -w`(프로세스별 CPU·컨텍스트 스위치) |
| 부가 | `vcgencmd measure_temp` / `get_throttled`(열 스로틀링), `/proc/loadavg` |
| 통제 | A·B 사이 **재부팅**으로 상태 초기화. 코드·설정·맵·임무 경로 동일 |

**CPU 표기**: 프로세스 CPU는 단일 코어 기준이다. `100%` = 코어 1개 완전 점유,
따라서 4코어 장비의 총량은 `400%`다. 시스템 사용률(mpstat)은 4코어 평균 백분율이다.

### 측정 스크립트 (요지)

```bash
PIDS=$(pgrep -d, -f "sllidar_node|/bringup|map_server|/amcl|lifecycle_manager|\
controller_server|smoother_server|planner_server|behavior_server|bt_navigator|\
waypoint_follower|velocity_smoother|agent_node|detector|precision_parking")

mpstat 1 60  > /tmp/_mp.$L &          # 시스템 전체
pidstat -u -w -p "$PIDS" 1 60 > /tmp/_ps.$L &   # 프로세스별 CPU + 컨텍스트 스위치
wait
```

## 7. 결과 해석

### 7-1. 순찰 주행 — CycloneDDS가 유의미하게 낫다

```
CPU 사용률        78.3%  →  73.4%    (−4.9%p)
user CPU          53.72  →  42.22    (−11.50%p)
프로세스 CPU 합계  270.57 →  236.38   (−34.19%p,  −12.6%)
bt_navigator      36.03  →  23.75    (−12.28%p,  −34%)
idle              21.66% →  26.61%   (+4.95%p 여유 확보)
```

**★게다가 B-2는 불리한 조건에서 이겼다** — 온도 79.8°C(A는 71.1°C), 시작 load 9.72(A는 6.70).
열·부하가 더 나쁜 상태에서도 CPU를 덜 썼다.

### 7-2. 정지 상태 — 상쇄되어 뚜렷하지 않다

```
프로세스 CPU 합계  243.82 → 220.67   (−23.15%p)   ← 개선
user CPU          46.93  → 39.76    (−7.17%p)    ← 개선
system CPU        21.38  → 29.72    (+8.34%p)    ← 악화
전체 사용률        68.5%  → 71.9%    (+3.4%p)     ← 소폭 악화
```

**user는 줄고 system은 느는 교환**이 일관되게 나타난다. 정지 상태에서는 이 둘이 상쇄된다.
다만 B-1은 온도 79.8°C·load 11.46에서 시작해 A-1(67.6°C·6.18)보다 불리했으므로,
**동일 조건이었다면 격차는 더 좁거나 역전됐을 가능성이 있다.**

### 7-3. 도킹 — 측정 무효 (열 스로틀링)

```
A-3b  throttled = 0x0        (스로틀링 없음)
B-3b  throttled = 0xe0008    ★soft temp limit 발생 + 주파수 캡 + 스로틀링 발생
      온도 83.2 → 82.3°C, 배터리 저하 상태
```

스로틀링이 걸리면 같은 부하에서도 처리량이 떨어져 CPU 수치가 왜곡된다.
**이 조건은 배터리 충전·냉각 후 재측정해야 한다.**

### 7-4. 종합 판단

| 조건 | 판정 | 근거 |
|---|---|---|
| **순찰 주행** | **CycloneDDS 우세** | CPU −4.9%p, 프로세스 합계 −12.6%, 불리한 열 조건에서 달성 |
| 정지 | 판단 유보 | user↓ / system↑ 상쇄, 조건 불일치 |
| 도킹+카메라 | **측정 무효** | 열 스로틀링 발생 |
| 컨텍스트 스위치 | **차이 없음** | 두 구현체 모두 노드당 150~190/s |

**결론**: 실제 주행 부하가 걸리는 구간에서 CycloneDDS가 유리하다는 신호가 관측됐다.
다만 **정지 조건의 조건 불일치와 도킹 조건의 스로틀링** 때문에, 채택 결정을 내리려면
**냉각 상태에서 3조건 재측정**이 필요하다.

**그리고 이 실험은 근본 병목이 DDS가 아님도 함께 보여준다** — 카메라(detector)가 약 142%,
Nav2 스택이 약 133%를 쓰는 구조에서 미들웨어 교체로 얻는 것은 두 자릿수 %p 수준이다.

## 8. 전환 과정에서 겪은 함정 4건

CycloneDDS 전환은 환경변수 하나로 끝나지 않았다. WiFi·다중 인터페이스 환경에서 네 번 막혔다.

### 함정 ① `ROS_STATIC_PEERS`가 디스커버리를 방해

```
증상  로봇에서는 PC 노드가 보이는데 PC에서는 로봇 노드가 안 보임(비대칭)
원인  Fast DDS 계열 설정. Cyclone 에서는 도움이 안 되고 간섭
조치  Cyclone 을 쓰는 셸에서 unset ROS_STATIC_PEERS
```

### 함정 ② WiFi 멀티캐스트로는 데이터가 전달되지 않음

```
증상  디스커버리 성공(노드·토픽 목록 보임)인데 topic echo 데이터 0건
원인  Cyclone 기본 AllowMulticast=true → 데이터도 멀티캐스트. WiFi AP가 사실상 차단
조치  <AllowMulticast>spdp</AllowMulticast>  (디스커버리만 멀티캐스트, 데이터는 유니캐스트)
      + <Peers> 에 상대 IP 명시
```
Fast DDS에서 `ROS_STATIC_PEERS`로 유니캐스트를 강제했던 것과 **같은 문제·같은 해법**이다.

### 함정 ③ 인터페이스 고정이 같은 호스트 통신을 끊음

```
증상  AllowMulticast=false + 원격 피어만 지정 → 로봇 내부 노드끼리도 서로 못 찾음
      (도메인 노드 수 0, /scan 연결 정보 없음 — 스택이 떠 있어도 기능적으로 죽은 상태)
원인  <Interfaces><NetworkInterface name="wlan0"/> 로 고정하면 루프백 경로가 빠짐
조치  인터페이스 고정을 제거하고 AllowMulticast=spdp 로 해결
```

### 최종 설정

```xml
<?xml version="1.0" encoding="UTF-8"?>
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain id="any">
    <General>
      <AllowMulticast>spdp</AllowMulticast>   <!-- 디스커버리만 멀티캐스트, 데이터는 유니캐스트 -->
    </General>
    <Discovery>
      <Peers><Peer address="상대_IP"/></Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
```
```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml
unset ROS_STATIC_PEERS
```

### 함정 ④ 이종 미들웨어는 통신되지 않는다

로봇을 Cyclone으로 바꾸자 **Fast DDS인 관제 PC와 통신이 완전히 끊겼다**(heartbeat 미수신).
ROS 2는 RMW 혼용을 보장하지 않는다. **한 시스템의 모든 참가자를 같은 구현체로 맞춰야 한다.**
→ 이 실험에서도 로봇 15개 프로세스 + PC 콘솔 + 웹앱 백엔드를 전부 전환한 뒤에야 측정이 가능했다.

## 9. 측정 신뢰성에 대한 기록

정직하게 남긴다.

1. **A와 B의 열·부하 조건이 완전히 같지 않다.** A는 부팅 17분·67.6°C, B는 재기동 반복 후 79.8°C에서 시작했다.
   → **B에 불리한 방향**이므로, 순찰에서 B가 이긴 결과는 보수적으로 해석해도 유효하다.
2. **도킹(B-3b)은 스로틀링으로 무효**다. 재측정 대상.
3. 측정 중 `pidstat` 출력 해석에서 두 번의 오독이 있었고 원본 데이터로 정정했다.
   - `%CPU`는 8번째 컬럼(4번째는 `%usr`)
   - `-u -w` 동시 출력 시 **Average 블록이 두 개**이며 뒤쪽이 컨텍스트 스위치
   → 이 문서의 모든 수치는 원본 `pidstat` 파일에서 재추출한 값이다.
4. 각 조건 1회 측정이다. 반복 측정으로 분산을 확인하지 않았다.

## 9-A. ★후속 실험 — 깨어남을 줄이는 튜닝 (미들웨어보다 큰 효과)

DDS 교체가 두 자릿수 %p 수준이라는 결론에 이어, **"무엇이 노드를 깨우는가"** 를 직접 추적했다.
결과적으로 **미들웨어 교체보다 이쪽이 더 확실한 이득**을 냈다.

### 9-A-1. 깨어남 유발원 실측

컨텍스트 스위치는 통신 미들웨어가 아니라 **발행 주기**에서 나온다. 실측하니 정확히 맞아떨어졌다.

| 토픽 | 주기 | 비고 |
|---|---:|---|
| **`/tf`** | **67.0 Hz** | 최대 유발원 |
| `/odom` | 30.1 Hz | |
| `/joint_states` | **50.6 Hz** | ★bringup은 30Hz만 내는데 50Hz — 중복 발행자 존재 |
| `/scan` | 10.1 Hz | |

`/tf` + `/odom` + `/scan` = **107회/초**. 여기에 각 노드의 타이머(10~20Hz)와 lifecycle bond(10Hz)를 더하면
관측된 `cswch/s 150~190`과 일치한다.

★**이것이 과거 튜닝이 실패한 이유도 설명한다.** controller 20→10Hz(+3.27%p), local costmap 10→5Hz(+1.48%p)로
타이머를 낮췄지만 **지배항인 `/tf` 67Hz를 건드리지 않아** 효과가 없었다.

### 9-A-2. `/tf` 67Hz의 정체 — 발행자 3개

```
/pinky_bringup          30Hz    odom → base_footprint   (bringup.py:88, 1/30 타이머)
/robot_state_publisher  ~30Hz   base → 바퀴 관절 TF     (joint_states 수신마다 재발행)
/amcl                   저빈도   map → odom
                        ─────
                        합계 ≈ 67Hz
```

`bringup.py`의 **단일 30Hz 타이머**가 TF·odom·joint_states를 한꺼번에 발행한다.

```python
# pinky_bringup/bringup.py:88
self.timer = self.create_timer(1.0 / 30.0, self.update_and_publish)
    → _publish_tf()            odom → base TF
    → _publish_odometry()      /odom
    → _publish_joint_states()  /joint_states
```

그런데 `/joint_states` 실측이 **50.6Hz** — bringup(30Hz) 외에 **`joint_state_publisher` 노드가 20.6Hz를 추가**하고 있었다.
이 노드는 URDF 기반 기본 발행자로, **엔코더 실측값이 아닌 값**을 낸다(2026-06-30 기록: 다른 joint 이름으로 0 발행).

## 9-B. ★3번째 로봇 교차검증 — 절대 수치는 하드웨어 세대에 좌우된다

로봇31(3번째 개체)에서 **같은 스택·같은 CycloneDDS·같은 JSP 제거 상태**로 재검증한 결과 CPU가 3분의 1로 나왔다.
처음에는 열 스로틀링 탓으로 판단했으나, **하드웨어를 확인하니 보드 세대가 달랐다.**

| | 로봇31 | 로봇44 · 50 |
|---|---|---|
| **보드** | **Raspberry Pi 5 Model B Rev 1.0** | Raspberry Pi 4 Model B Rev 1.5 |
| CPU | Cortex-A76 | Cortex-A72 |
| **최대 클럭** | **2,400 MHz** | 1,800 MHz |
| 코어 | 4 | 4 |
| 측정 시 온도 | 56~59°C | 70~81°C |
| `throttled` | 관측 불가(`/dev/vcio` 없음) | **0x80000** (soft temp limit 이력) |

**3배 차이의 주원인은 하드웨어 세대다.** RPi5는 클럭이 1.33배 높고 A76은 A72 대비 IPC가 크게 앞서,
같은 작업의 `%CPU`가 2~3배 낮게 나온다. **열 스로틀링은 부차적 요인**이다.

★이 문서의 §1~§9-A 측정은 **전부 RPi4(로봇44·50)** 에서 이뤄졌다.

| throttled | 측정 불가 ※※ | — | — | **0x80000** | 0x80000 | 0x80000 |
| load 시작 | 3.18 | 4.32 | 2.64 | 4.21 | 8.30 | 8.69 |

※ 로봇31 도킹은 detector가 측정창을 벗어나 합계에 미포함(시스템 사용률과의 차이 ≈ 53%가 detector 몫으로 추정).
※※ 로봇31은 `/dev/vcio`가 없어 `vcgencmd` 사용 불가. 온도는 `/sys/class/thermal`로 대체.

### 9-B-2. 프로세스별 — 라이다 노드가 12배 차이

| 프로세스 (순찰 중) | 로봇31 | 로봇44 | 비율 |
|---|---:|---:|---:|
| bringup | 16.03 | 29.54 | 54% |
| bt_navigator | 9.23 | 26.92 | 34% |
| lifecycle_manager | 9.30 | 26.04 | 36% |
| amcl | 7.85 | 17.59 | 45% |
| controller_server | 7.40 | 19.09 | 39% |
| **sllidar_node** | **1.93** | **24.83** | **8%** ★ |
| robot_state_publisher | 0.92 | 2.35 | 39% |
| **합계** | **92.28** | **245.34** | **38%** |

**동일 드라이버·동일 10Hz인 `sllidar_node`가 12배 차이**난다.
세대 성능차(2~3배)만으로는 설명이 안 되는 폭이므로, **RPi4의 열 스로틀링이 여기에 겹친 것**으로 봤다.
(로봇44는 측정 내내 `throttled=0x80000`, 70~81°C였다.)

> ⚠️ **이 추정은 §9-C-5에서 반증됐다.** 스로틀링이 없는 로봇87(RPi4)이 오히려 **29.44**로 더 높았다.
> 이 격차는 열이 아니라 **순수한 보드 성능차**다.

### 9-B-3. 스택 동작 자체는 동일하다

```
로봇31   정지  81.52 → 순찰  92.28    +10.76  (+13.2%)
로봇44   정지 221.66 → 순찰 245.34    +23.68  (+10.7%)
```
**주행이 추가로 만드는 부하 비율은 두 로봇이 거의 같다.** 즉 스택 동작 자체는 동일하며,
차이는 전부 **바닥값(상시 비용)** 에 있다. 그 바닥값을 가르는 것이 **보드 성능**이다.

### 9-B-4. ★`tag_lost`는 CPU 부하 문제로 확정

같은 코드·같은 태그·같은 도킹 절차인데 결과가 갈렸다.

| | 로봇31 | 로봇44 |
|---|---|---|
| 도킹 중 idle | **63.61%** | **7.53%** |
| 상태 전이 | `NAV → SEARCH_TAG → TAG_SERVO_ALIGN → SETTLE → **DONE**` | `TAG_SERVO_ALIGN → **FAILED(tag_lost)**` |
| 결과 | **완주** | 실패(육안으로는 정차 성공) |
| 온도 변화 | 59.5 → **56.8°C**(하강) | 77.9 → **81.3°C**(상승) |

→ **CPU 여유가 있으면 정렬 단계를 끝까지 통과한다.**
§9-A-6에서 "원인은 CPU가 아닌 다른 요인(FOV 잘림 등)으로 좁혀진다"고 적었던 추정은 **틀렸다. 정정한다.**
2026-07-27에 로봇31(load 4.05)이 성공하고 로봇50(load 9~13)이 실패했던 기록과도 일치한다.

★**원인이 클럭(보드 세대)이든 열이든, "CPU 여유 부족이 도킹 실패로 이어진다"는 인과는 동일하다.**
오히려 더 분명해진다 — **RPi4에는 이 스택이 빠듯하고, RPi5에서는 여유롭다.**

### 9-B-5. 이 발견이 앞선 결론에 미치는 영향

| 결론 | 판정 | 이유 |
|---|---|---|
| **JSP 제거 효과** (−19.01%p) | ✅ **유효** | 동일 로봇·동일 조건 전후 비교 |
| **CycloneDDS 순찰 개선** (−34.19%p) | ✅ **유효** | 동일 로봇 A/B |
| **"정지 상태 4코어의 61% 소비"** | ⚠️ **RPi4 한정** | RPi5(로봇31)에서는 **20%**(81.52/400) |
| **"detector 87.91%"** | ⚠️ **RPi4 기준 상한값** | RPi5에서는 절반 이하로 추정 |
| **`tag_lost` 원인** | ✅ **CPU 여유 부족으로 확정** | §9-B-4 |
| 컨텍스트 스위치 절대값 | ⚠️ 보드·클럭 영향 | 같은 보드 안에서만 비교할 것 |
| **서로 다른 로봇 간 절대값 비교** | ❌ **불가** | 보드 세대가 다르면 %CPU 자체가 다른 척도다 |

### 9-B-6. 진짜 우선순위가 바뀌었다

```
기존 판단   detector(88%) > Nav2 스택 > joint_state_publisher(17%) > 미들웨어
1차 정정    보드 세대(RPi4 vs RPi5) > detector > JSP 제거 > 미들웨어 > (RPi4의 냉각)
★최종 정정  RPi4 냉각 관리 > detector > JSP 제거 > 미들웨어 > (보드 교체는 마지막)   ← §9-C
```

**같은 코드가 RPi5에서는 CPU 4분의 1로 돈다.** 다만 **이것이 곧 "보드를 바꿔야 한다"는 뜻은 아니다** —
4번째 로봇(87)이 그 반례를 제공했다(§9-C).

**후속 조치 후보**
1. **RPi4의 냉각 관리** — 로봇87은 RPi4임에도 `throttled=0x0`을 유지해 **도킹을 완주**했다(§9-C)
2. **detector 최적화** — 단일 최대 소비자
3. **JSP 제거·미들웨어 튜닝** — 검증된 −19%p·−34%p
4. `vcgencmd get_throttled`를 **운영 점검 항목에 상시 포함** — 측정·판정 전에 먼저 확인
5. 로봇31(RPi5)에 `/dev/vcio` 생성(`sudo mknod /dev/vcio c 100 0`)해 스로틀링 관측 가능하게
6. **로봇 간 절대 성능 비교 금지** — 보드 세대를 명시하지 않은 비교는 무의미하다

## 9-C. ★4번째 로봇(87)으로 재정정 — RPi4로도 도킹이 완주한다

로봇87은 **RPi4이면서 `throttled=0x0`**(스로틀링 이력 없음)인 유일한 개체다.
§9-B에서 분리하지 못했던 **"보드 세대 vs 열 상태"** 를 가르는 대조군이 됐다.

### 9-C-1. 세 조건 측정 (CycloneDDS · JSP 0개)

| 지표 | **로봇31** RPi5 | **로봇87** RPi4 `0x0` | **로봇44** RPi4 `0x80000` |
|---|---:|---:|---:|
| 정지 CPU / 합계 | 25.5% / 81.52 | **61.1% / 215.22** | 66.1% / 221.66 |
| 순찰 CPU / 합계 | 26.2% / 92.28 | **67.4% / 239.07** | 70.3% / 245.34 |
| 도킹 CPU / **idle** | 35.2% / **63.61%** | 79.4% / **20.58%** | 90.1% / **7.53%** |
| 순찰 증가폭 | +10.76 (13.2%) | **+23.85 (11.1%)** | +23.68 (10.7%) |
| 온도(정지→도킹) | 56.8 → 59.5°C | 57.5 → **75.5°C** | 70.6 → **81.3°C** |
| **도킹 결과** | **DONE 완주** | **DONE 완주** ★ | **`tag_lost` 실패** |

### 9-C-2. 결론 1 — 정지 상태에서 열의 기여는 3%뿐

```
같은 RPi4끼리   정지 215.22 vs 221.66   차이 3.0%   (스로틀링 유무에도 불구)
                순찰 239.07 vs 245.34   차이 2.6%
RPi4 → RPi5     정지 215.22 vs  81.52   차이 62%
```
**정지·순찰의 절대값을 가르는 것은 보드 세대**이고, 열은 3% 남짓이다.

### 9-C-3. 결론 2 — 그러나 도킹 성패는 열이 갈랐다

```
로봇87 RPi4  throttled=0x0      도킹 idle 20.58%  →  DONE 완주
로봇44 RPi4  throttled=0x80000  도킹 idle  7.53%  →  tag_lost 실패
```
**같은 보드인데 결과가 갈렸다.** 정지 측정에서는 3%였던 차이가, **부하가 몰리는 도킹 구간에서는 성패를 가른다.**
정지 측정만으로는 보이지 않는 차이다.

### 9-C-4. ★"보드 교체가 답"이라는 결론은 철회한다

§9-B 초안에서 "보드 교체의 효과가 압도적"이라고 썼으나, **로봇87이 RPi4로 도킹을 완주**하면서 반증됐다.

```
idle 63.61%(RPi5)  → 완주
idle 20.58%(RPi4)  → 완주    ← ★RPi4로도 된다
idle  7.53%(RPi4)  → 실패
```
**임계는 보드가 아니라 CPU 여유다.** RPi4라도 **여유가 20% 남으면 도킹이 완주**한다.
따라서 실용적 우선순위는 **냉각 관리 → detector 최적화 → JSP 제거·미들웨어 튜닝**이며,
보드 교체는 마지막 수단이다.

### 9-C-5. `sllidar_node` 격차도 재정정

| | 로봇31 RPi5 | 로봇87 RPi4 `0x0` | 로봇44 RPi4 `0x80000` |
|---|---:|---:|---:|
| 정지 | 1.93 | **29.44** | 24.79 |
| 순찰 | 1.93 | **26.99** | 20.41 |

**스로틀링이 없는 로봇87이 오히려 더 높다.** §9-B-2에서 "세대차를 넘으므로 열 스로틀링이 겹친 것"이라고
쓴 추정은 **반증됐다** — 이 격차는 **순수한 보드 성능차**다(시리얼 I/O·인터럽트가 잦은 작업에서 A76과 A72의
차이가 더 벌어지는 것으로 보인다).

### 9-C-6. 부수 확인 — agent만 다른 미들웨어면 도킹이 통째로 멈춘다

로봇87 1차 도킹이 `nav_timeout`으로 실패했는데, 원인은 성능이 아니었다.

```
bt_navigator(Nav2)  librmw_cyclonedds_cpp
agent_node          librmw_fastrtps_cpp    ← Cyclone 소싱 안 된 터미널에서 기동
  → agent 가 띄운 precision_parking 도 FastDDS 상속
  → navigate_to_pose 액션 서버를 못 봄 → nav_status=pending 영구 유지
  → 60초 후 NAV_CANCELING → FAILED(nav_timeout), 로봇은 한 번도 안 움직임
```
`/cmd_vel_nav`가 비어 있고 `/scan`·`/amcl_pose`는 정상인 조합이 이 증상의 지문이다.
→ §8 함정 ④(RMW 혼용 불가)의 구체 사례. **agent 재기동 후 도킹은 DONE 완주.**

## 부록 A. 재현 방법

```bash
# 1) 설치
sudo apt install ros-jazzy-rmw-cyclonedds-cpp

# 2) 설정 (로봇·PC 양쪽, 상대 IP만 다르게)
cat > ~/cyclonedds.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<CycloneDDS xmlns="https://cdds.io/config"><Domain id="any">
  <General><AllowMulticast>spdp</AllowMulticast></General>
  <Discovery><Peers><Peer address="192.168.2.5"/></Peers></Discovery>
</Domain></CycloneDDS>
EOF

# 3) 전환 (스택을 띄우는 모든 터미널에서)
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml
unset ROS_STATIC_PEERS

# 4) 실제 적용 확인 — 환경변수가 아니라 로드된 라이브러리로 검증
grep -o "librmw_[a-z_]*" /proc/<PID>/maps | sort -u

# 5) 원복
unset RMW_IMPLEMENTATION CYCLONEDDS_URI   # 후 스택 재기동
```
