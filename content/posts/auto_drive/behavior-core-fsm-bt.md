로봇이 "지금 무엇을 하는가"를 결정하는 계층을 **행동코어(behavior core)** 라고 부르기로 했다.
단일 알고리즘이 아니라 골격이다. 요구를 정리하면 다섯 줄이었다.

| 요구 | 의미 |
|---|---|
| 모드/상태 선택 | 대기 · 순찰 · 선생님보조 |
| 자동/수동 전이 | 인지 이벤트와 GUI 명령 양쪽을 받는다 |
| 상태별 임무 실행 | 그 상태에서 무엇을 어떻게 수행·복구하는가 |
| 긴급정지 | 어느 상태·임무 중에도 즉시 중단 |
| 다중 로봇 관제 | 상태를 콘솔과 동기화 |

결론부터 적는다. **설계는 2계층이었고, 구현은 아래 한 층뿐이다.**
순찰 FSM과 도킹 FSM은 만들어서 실기 검증까지 마쳤고, 그 위에서 모드를 소유하는 조율 계층은 만들지 않았다.
2026-06-29 조사 결론이었던 YASMIN 과 BehaviorTree.CPP v4 는 **둘 다 저장소에 없다.**

이 글은 그 절반이 어떻게 만들어졌고 나머지 절반이 왜 비었는지에 대한 기록이다.

---

## 1. 왜 2계층인가

FSM 하나로 다 하려고 하면 전이표가 폭발한다. "순찰 중 goal 이 abort 됐고, 배터리가 낮고,
앞에 로봇이 있고, 재측위가 필요한" 조합을 전부 상태로 승격시키면 상태가 곱셈으로 늘어난다.

반대로 BT 하나로 다 하려고 하면 **"지금 어느 모드인가"라는 시스템 상태의 소유자가 애매해진다.**
BT 는 매 tick 루트부터 다시 평가하는 구조라, 오래 유지되는 배타적 모드를 표현할 자리가 마땅치 않다.

그래서 역할을 갈랐다.

- **FSM** — "언제 어느 상태인가" (모드 전이, 운영자 개입, 긴급정지)
- **BT** — "그 상태에서 어떻게 수행·복구하는가" (재계획, 재시도, fallback)

근거로 본 것은 네 가지였다. FSM–BT 비교 연구(과제 복잡도가 커질수록 BT 가 유지보수에서 유리하다는 결과),
BT survey(모듈성·재사용성), Flexible Behavior Trees(HFSM 의 상태가 BT 를 로드/실행하는 하이브리드),
그리고 현업 최대 사례인 **Nav2 자체가 BehaviorTree.CPP 기반**이라는 사실.

마지막 항목이 나중에 이 설계를 반쯤 무의미하게 만든다. 아래에서 다시 다룬다.

## 2. 계층 지도 — 어디까지 만들었나

{{< figure src="/images/diagrams/autodrive-behavior-core-layers.svg" alt="행동코어 계층 지도. 최상위 B0 상위 FSM 은 미구현이고 agent 가 모드 문자열을 중계할 뿐이며, 그 아래 순찰 FSM 과 도킹 FSM 두 개만 구현·검증됐다. 통행 중재기는 FSM 이 아닌 규칙 엔진이고, 주행 임무는 Nav2 bt_navigator 에 위임하며, E-STOP 은 FSM 계층 밖에서 모터 직전을 래치한다." >}}

| 계층 | 설계상 역할 | 현황 |
|---|---|---|
| **B0 상위 FSM** | 모드 전이 · 운영자 개입을 소유 | **미구현** — agent 의 모드 문자열 중계 + 각 노드의 자체 판단으로 대체 |
| **하위 실행 상태기계** | 순찰 · 도킹의 실제 수행과 실패 처리 | **구현 · 실기 검증 완료** — 순수 FSM 2종 |
| **B1 BT 실행기** | 상태 내부 임무의 수행 · 복구 | **Nav2 `bt_navigator` 에 위임** (자체 구현 없음) |
| **전역 오버레이** | 어느 상태에서든 우선하는 정지 | 구현 — FSM 밖, 모터 직전 최종단 래치 |

점선은 조율이 아니라 **문자열 중계**다. agent 가 `/wasab/cmd_mode` 를 받아 로컬 도메인으로 재발행하면,
그 문자열을 보고 무엇을 할지는 각 노드가 따로 판단한다. 두 FSM 은 서로의 존재를 모르고,
둘을 조정하는 주체는 없다. 통합된 단일 행동코어 노드는 만들지 않았다.

## 3. "상태를 들고 있다"와 "상태기계다"는 다르다

발표 자료를 쓰면서 가장 먼저 한 일이 이 구분이었다. 상태 비슷한 것을 들고 있는 모듈은 여럿인데,
그중 실제로 **명시적 상태 라벨과 전이표**를 가진 것은 둘뿐이다.

| 대상 | 명시적 상태 · 전이 | 분류 |
|---|---|---|
| `patrol_planner.PatrolPlanner` | `PATROL` ↔ `YIELD`, 반환에 `WAIT_EDGE` | **FSM** |
| `state_machine.py` (도킹) | `IDLE` → `NAV_TO_APPROACH` → … → `DONE` / `FAILED` | **FSM** |
| `relocalize_logic.RelocalizeState` | `_armed` 불리언 + cooldown · 이동거리 조건 | 2상태 **래치** |
| `traffic_rules.Arbiter` | 상태 라벨 없음. `GRANTED/QUEUED/REJECTED` 는 중재기의 상태가 아니라 **요청에 대한 응답** | **규칙 엔진 + 점유표** |
| E-STOP | 불리언 래치 (모터 직전 최종단) | 오버레이 |
| 모드 `idle`/`patrol`/`assist` | 문자열 relay, 전이 로직 없음 | 오버레이 |

특히 통행 중재기를 FSM 으로 부르지 않는 이유가 중요하다. `GRANTED / QUEUED / REJECTED / REVOKED`
는 VDA 5050 3.0.0 의 상태 모델을 그대로 쓴 것이지만, 그건 **중재기 자신의 상태가 아니라 개별 요청에 대한 응답**이다.
중재기는 전이표를 갖지 않고 매 tick 점유표를 처음부터 다시 계산해 판정만 한다. 구조상 규칙 엔진이다.
알고리즘 자체는 [좌표를 버리고 홉으로 센 통행 중재기](../다중로봇-통행중재-홉기반-점유와-실측규칙/)에 따로 적었다.

## 4. 순찰 FSM — `PatrolPlanner`

ROS 의존이 0인 순수 모듈이다. 3상태.

| 상태 | 의미 | 전이 |
|---|---|---|
| `PATROL` | 웨이포인트 순회 주행 | 타 로봇이 `yield_radius` 안 → `YIELD` |
| `YIELD` | 하드 정지 + goal cancel | 모두 `clear_radius` 밖 → `PATROL` (**히스테리시스**) |
| `WAIT_EDGE` | 통행 승인 대기 | 승인(`go`) → 다음 노드 전진 |

설계에서 지킨 것 세 가지.

- **순찰 로봇은 최하위 우선순위다.** 아레나가 좁으므로 '비켜 돌기'는 하지 않고 정지만 한다.
  비켜 돌 공간이 없는 곳에서 회피 궤적을 만들면 벽으로 간다.
- **`gate` 는 노드에 도착했을 때만 의미를 갖는다.** 막힌 구간에는 애초에 들어가지 않는다(fail-closed).
  들어간 뒤에 취소하는 것보다 안 들어가는 쪽이 언제나 싸다.
- **시작 노드는 현재 위치의 최근접 노드다.** 임의 지점에서 순찰을 걸어도 링에 올라탄다.

히스테리시스는 생성자에서 `clear_radius ≥ yield_radius` 를 강제한다. 두 반경이 같으면
경계에서 상태가 떨리고, 떨리는 상태기계는 `goal cancel` 과 `goal 재발행`을 초당 몇 번씩 반복한다.

## 5. 도킹 FSM — `state_machine.py`

8상태 + `ESTOP`. 역시 순수 모듈이다.

{{< figure src="/images/diagrams/autodrive-docking-fsm-states.svg" alt="도킹 FSM 8상태 흐름과 제어 소유권. NAV_TO_APPROACH 와 NAV_CANCELING 구간은 Nav2 가 cmd_vel 을 소유해 정밀주차 노드의 발행이 금지되고, TAG_SERVO_ALIGN 과 SETTLE 구간은 정밀주차 노드가 pose regulation 으로 소유한다." >}}

| 상태 | 의미 |
|---|---|
| `IDLE` | goal 대기 |
| `NAV_TO_APPROACH` | Nav2 접근 주행 (경유점 라우팅 포함) |
| `NAV_CANCELING` | Nav2 goal 취소 대기 |
| `SEARCH_TAG` | 목표 AprilTag 탐색 (여기서 detector 서브프로세스 기동) |
| `TAG_SERVO_ALIGN` | tag pose 오차 기반 PID 정렬 |
| `SETTLE` | tolerance 유지 확인 |
| `DONE` / `FAILED` | 종료 상태 |
| `ESTOP` | E-STOP 래치. **순수 모듈이 아니라 `precision_parking_node` 가 설정한다** |

### 소유권 분리

`NAV_TO_APPROACH` 와 `NAV_CANCELING` 은 Nav2 가 `/cmd_vel` 을 소유하는 구간이라,
정밀주차 노드는 이 구간에서 **발행 자체를 금지**한다(`_NO_PUBLISH`).
두 제어기가 같은 토픽에 동시에 쓰면 로봇이 진동한다. 상태 라벨이 곧 소유권 표기다.

### `TAG_SERVO_ALIGN` 은 P 제어가 아니다

여기가 단순 비례 제어였다면 좌우로 어긋난 상태에서 제자리 회전만 반복했을 것이다.
diff-drive 는 횡방향 속도가 없어서 **제자리 회전으로 좌우 offset 을 병진 보정할 수 없다.**
그래서 극좌표 추종(ρ, α, β)의 **pose regulation** 으로 갔다. 로봇이 호를 그려
태그 법선 위로 올라타면서 `ey` → 0, `eyaw` → 0, `ex` → 0 순으로 수렴한다.

yaw 는 한 겹 더 필요했다. 평면 마커는 정면에 가까울수록 pose 해가 ±flip 하는 성질이 있어
`eyaw` 가 `+0.09 / −0.09` 로 교대하고 `wz` 가 요동쳤다. `YawFilter`(최근 6개 yaw 의 circular mean)로
**x/y 는 raw, yaw 만 필터**해서 잡았다. 병진 오차까지 필터를 먹이면 수렴이 느려진다.

**결과** — 태그 4개(7·8·9·10)에서 정면 15 cm 정차, `ex` **6~12 mm** · `ey` **< 4 mm** 물리 검증(2026-07-11).
제어기 유도와 튜닝 과정은 [Nav2로 가까이, AprilTag PID로 정확히](../nav2-apriltag-pid-정밀도킹-성공기록/)에 자세히 적었다.

## 6. 전역 오버레이 — E-STOP

정지는 상태 전이로 만들지 않았다. 어느 상태에서 눌러도 통해야 하는데, 그러려면
모든 상태에 정지 전이를 달아야 하고, 그건 다시 전이표 폭발이다.
그래서 **FSM 계층을 아예 통과하지 않는 경로**로 뺐다.

| 단계 | 내용 |
|---|---|
| 1 | 웹앱 정지 버튼 → `POST /api/cmd/estop` |
| 2 | 백엔드가 `/wasab/estop` 발행 (콘솔 도메인 50) |
| 3 | `estop_relay` — 로봇에서 도는 **독립 프로세스**(systemd), 로봇 도메인으로 재발행 |
| 4 | `bringup`(base)이 모터 0 래치 + 이후 `cmd_vel` 무시 |

**이 프로젝트에서 로봇 파일을 수정한 유일한 지점**이 4단계다. `bringup.py` 에 래치 **4줄**
(estop 구독 + `twist_callback` 맨 앞 차단). 모터 직전 최종단이라야 어떤 상태에서든 확실히 멈추기 때문에
여기만 예외로 뒀고, 로봇마다 `bringup.py` 버전이 달라 파일을 덮어쓰지 않고 스니펫만 삽입했다.

릴레이를 agent 와 **완전히 분리된 프로세스**로 둔 것도 의도적이다.
안정 운용 중인 agent 소스를 건드리지 않으면서, agent 가 죽어도 정지는 살아 있게 하는
두 조건을 동시에 만족하는 방법이 이것뿐이었다.

파서도 둘로 갈랐다. `parse_estop` 은 **넓게** 받아서 정지하고,
`parse_estop_msg` 는 **엄격**해서 파싱 실패 시 `None` 을 낸다.
정지는 애매해도 걸어야 하고, 해제는 손상된 메시지 때문에 잘못 풀리면 안 된다.

## 7. 시행착오

### 사례 1. 꺼진 로봇의 잔상 때문에 순찰이 영구 정지했다

- **문제** — 다른 로봇을 끄고 나서도 순찰 로봇이 `YIELD` 에서 나오지 못했다. 주변에 아무도 없었다.
- **접근** — `YIELD` 조건은 "타 로봇이 반경 안에 있음"이다. 실제로 없는데 조건이 참이면
  참조하는 **데이터가 낡은 것**이다. heartbeat 캐시를 열어보니 이미 종료된 로봇의 마지막 좌표가 그대로 있었다.
- **해결** — 타 로봇 pose 에 TTL 을 걸었다(`HEARTBEAT_TTL_S = 1.5`). 1.5초보다 오래된 좌표는 판정에서 뺀다.

### 사례 2. 로봇이 자기 자신을 보고 양보했다

- **문제** — 로봇 한 대만 띄웠는데 즉시 `YIELD` 로 빠져 움직이지 않았다.
- **접근** — 타 로봇 목록을 만들 때 heartbeat 에서 자기 id 를 제외하는데,
  `PATROL_ROBOT_ID` 가 설정되지 않으면 id 가 0 이 되어 **자기 heartbeat 를 타 로봇으로 오인**한다.
  자기 자신과의 거리는 0 이므로 항상 yield 조건에 걸린다.
- **해결** — `robot_id <= 0` 이면 기동 시점에 **명시적으로 실패**시켰다.
  설정 누락이 조용히 잘못된 동작으로 이어지는 것이 가장 나쁘다.

### 사례 3. 막힌 노드를 건너뛰게 했더니 아레나 한가운데서 충돌했다

- **문제** — 처리량을 높이려고 막힌 노드를 건너뛰는(skip) 동작을 넣었다.
  인덱스가 2씩 늘면서 `tag7→S`, `S→tag10` 같은 **링에 존재하지 않는 대각선 엣지**를 주행했다.
  중재기가 모르는 경로라 아무도 막지 못했고 아레나 한가운데서 충돌했다.
- **접근** — 충돌 지점이 링 위가 아니라는 데서 출발했다. 중재기의 점유 모델은 **링 그래프의 엣지**만 안다.
  로봇이 그래프에 없는 경로를 달리면 점유를 표현할 방법 자체가 없다.
- **해결** — 건너뛰기를 제거했다. **판정 가능한 상태 공간 밖으로 나가는 동작은 안전을 보장할 수 없다.**

### 사례 4. 처리량을 얻으려다 추돌했다

- **문제** — 엣지 위 로봇이 가까운 끝점 하나만 잠그게 해 점유를 1.79 → 1.00 노드로 줄였다.
  앞차가 긴 엣지 중간을 넘는 순간 뒤쪽 노드가 열려, 뒤차가 **0.7 m** 뒤까지 따라붙어 tag10 부근에서 추돌했다.
- **접근** — 최적화의 전제("엣지 중간을 지나면 뒤 노드는 비어 있다")가 물리적으로 틀렸다.
  로봇은 점이 아니고 통로는 좁다.
- **해결** — 되돌렸다. 처리량 최적화는 물리적 여유가 있을 때만 유효하다.

### 사례 5. 도킹만 상습적으로 끼었다 — 같은 Nav2인데 순찰은 통과했다

- **문제** — `tag9→tag7` 도킹 접근 구간에서 반복적으로 끼었다.

  ```text
  collision ahead                                        100+ 회
  Controller patience exceeded → follow_path Aborting     13 회
  costmap clear · spin · backup · wait                    복구 전부 실패
  → abort 무한 루프, error_code 104
  ```

  그런데 **순찰은 같은 구간을 잘 통과**했다.
- **접근** — 처음엔 동적 장애물 회피 문제로 봤다가, 사용자 지적으로 재정의했다 —
  *"이 구간은 박스와 무관하게 원래 못 뚫던 상습 끼임 구간이다."*

  두 경로가 **동일한 `navigate_to_pose`**(같은 플래너 · 컨트롤러 · goal checker)를 쓴다.
  즉 Nav2 파라미터 차이가 아니었다. 차이는 **라우팅**이었다.

  | | 순찰 (통과) | 도킹 (끼임) |
  |---|---|---|
  | 목표 발행 | 순차 웨이포인트 tag9 → **tag10(최북단)** → tag7 | **단일 직행** → tag7 approach |
  | 진행 | `reach_tol 0.15` **pass-through** (타이트한 pose 에 눌러앉지 않음) | approach **정확 도달까지 대기** |

  그리고 approach pose 는 임의값이 아니었다. PID 정밀주차를 위해 **태그 가시 + 직선 진입** 조건을
  만족해야 하는 저지대 지점이라, 순찰처럼 근처를 스쳐 지나가는 것으로 대체할 수 없었다.
- **해결** — 로봇 파일을 변경하지 않고 PC 에서 순차 goal 을 발행해 경유점 라우팅을 먼저 실증했다.

  | leg | 구간 | 결과 |
  |---|---|---|
  | 1 | tag9 → staging tag10 | SUCCEEDED |
  | 2 | staging → tag7 북쪽 | SUCCEEDED (**직행 땐 여기서 abort**) |
  | 3 | tag7 북쪽 → 실제 approach | SUCCEEDED, `error_code 0`, patience · abort · spin/backup **0** |

  실증 후 `pre_waypoints` 로 최소 구현했다. **FSM 은 한 상태도 바꾸지 않았다** —
  `NAV_TO_APPROACH` 안에서 목표를 순차로 넘길 뿐이다.
- **남긴 것** — 같은 스택이 어떤 경로는 통과하고 어떤 경로는 못 뚫으면,
  스택 파라미터가 아니라 **주는 목표의 형태**를 먼저 본다.

### 사례 6. agent CPU가 도킹을 막았다 — "TF가 무겁다"는 틀린 가설

- **문제** — 콘솔 버튼으로 도킹을 걸면(agent ON) 실패하고, agent 를 끄면 성공했다.
  agent 프로세스가 CPU 를 30% 가까이 먹으면서 Nav2 planner 를 기아 상태로 만들고 있었다.
- **접근** — "TF 계산이 무겁다"는 가설을 세웠다가, 짐작 대신 **단일 변수로 격리해 측정**했다.
  방금 부팅한 예비 로봇에 bringup 만 띄우고(구독 대상 중 발행자가 있는 토픽이 `/tf` 하나뿐인 상태)
  그 위에 agent 1벌만 올렸다. `top -H` 로 스레드별, `py-spy` 로 함수별 프로파일을 떴다.

  | 함수 | 비중 |
  |---|---|
  | `_wait_for_ready_callbacks` (rclpy 실행기) | **≈ 85 %** |
  | `lookup_transform` / `can_transform` (실제 TF 수학) | **≈ 0 %** |

  가설이 틀렸다. TF 연산은 공짜였다. 진짜 원인은 **rclpy 실행기가 `spin_once` 마다 wait-set 을
  Python 으로 재구성**하는 비용이었고, 이를 초당 35번 깨우는 주체가 **35 Hz `/tf`** 였다.
  `map→base` 를 TF 로 얻으려면 `odom→base`(bringup 35 Hz)를 소비할 수밖에 없다.
- **해결** — pose 의 **용도**를 확인했다. 이 pose 는 콘솔 마커 표시용(2 Hz 소비)일 뿐
  **도킹 제어에는 전혀 쓰이지 않는다.** 그래서 pose 소스를 TF 에서 `/amcl_pose` 구독으로 바꿨다.
  wake 빈도가 35 Hz → AMCL 발행 주기로 떨어졌다.

  **robot_ctx CPU 30% → 8%**, 콘솔 버튼 도킹 tag7→tag9 완주 검증.
- **남긴 것** — "무거워 보이는 것"과 "실제로 무거운 것"은 다르다. 프로파일 없이 최적화하지 않는다.
  이 건의 전체 맥락은 [두 ROS 도메인을 잇는 agent와 CPU 튜닝](../wasab-로봇함대-두-도메인을-잇는-agent와-cpu튜닝/)에 있다.

### 사례 7. 재측위가 조용히 타임아웃했다 — 원인이 세 번 달랐다

- **문제** — AprilTag 재측위가 타임아웃하는데 매번 원인이 달랐고, 매번 "코드 문제"로 의심했다.
- **접근 · 해결** — 세 번 모두 코드가 아니었다.

  | 회차 | 겉보기 | 실제 원인 | 판별법 |
  |---|---|---|---|
  | ① | 재측위 타임아웃 | `localization` 을 `use_composition:=True` 로 기동 | composed 면 `/initialpose`→AMCL 경로가 실패. `False` 필수 |
  | ② | 타임아웃 (IP · 설정 · 소스 전부 정상, md5 까지 동일) | detector 640×480 crop FOV 에 **태그가 너무 커서 상단이 잘림** | 1280 은 디코드되는데 640 preview 가 안 되면 확정. 로봇을 뒤로 |
  | ③ | 타임아웃인데 detector 는 `tag_id` 를 정상 디코드 | `relocalizer.yaml` 의 `map_name` 이 현재 맵과 불일치 | 로그에 "map 불일치 skip" 이 직접 찍힘 |

- **남긴 것** — 검증된 것(소스 · md5)이 같다면 **다른 것**을 찾아야 한다. 소스부터 의심하면 시간을 버린다.
  그리고 **"조용한 skip"은 반드시 로그를 남겨야 한다** — ③은 로그가 있어서 즉시 잡혔다.

### 사례 8. 정지시켰더니 순찰이 영영 안 됐다

- **문제** — 긴급정지 후 순찰을 다시 시작해도 로봇이 움직이지 않았다. Nav2 는 정상이고 `/cmd_vel` 에 값도 나갔다.
- **접근** — 명령은 나가는데 바퀴가 안 도는 상황이므로 **최종단**을 봤다.
  E-STOP 은 base 가 `cmd_vel` 을 무시하는 **래치**다. 즉 설계대로 동작 중이었고, 해제를 안 보낸 것이 문제였다.
- **해결** — 프런트에 **정지 해제** 버튼을 명시적으로 두고, 해제 시 `active:false` 를 발행하게 했다.
  운영 문서에도 "정지 후 해제하지 않으면 순찰이 먹통"을 적었다.
  래치는 설계 의도대로 동작할 때조차 **해제 UI 가 없으면 버그처럼 보인다.**

### 사례 9. Nav2가 goal을 거부/중단하면 상태기계가 멎었다

- **문제** — Nav2 가 goal 을 reject 하거나 abort 하면 순찰 노드가 다음 동작을 못 하고 멈춰 있었다.
- **접근** — 상태기계가 goal 발행 후 **결과를 상태로 추적하지 않고** 있었다. 성공만 가정한 설계였다.
- **해결** — goal 상태 추적을 넣고 reject/abort 시 **2초 백오프 후 재시도**하게 했다(`GOAL_RETRY_BACKOFF_S = 2.0`).
  즉시 재시도는 같은 실패를 반복하며 CPU 만 먹는다.
  추가로 Nav2 가 20초간 응답 자체를 주지 않으면 `goal_pending_stuck` 으로 **pause + 운영자 알림**을 낸다.
  무한 재시도로 조용히 도는 것보다 사람을 부르는 편이 낫다.

### 사례 10. 상태기계는 정상인데 로봇만 안 움직였다

- **문제** — Nav2 전체가 정상 동작하고 `/cmd_vel_nav` 에 값이 나오는데 로봇이 안 움직였다.
- **접근** — `/cmd_vel_nav` 에는 값이 있고 `/cmd_vel` 은 비어 있었다. 두 토픽 사이에 있는 것은 `velocity_smoother` 다.
- **해결** — `velocity_smoother` 의 lifecycle 이 `inactive` 였다. 활성화로 해결(재부팅 불필요).
- **남긴 것** — "Nav2 가 도는데 로봇만 안 간다" → **`velocity_smoother` lifecycle 을 먼저** 본다.

## 8. 조사 결론을 쓰지 않았다

2026-06-29 조사 결론은 **"YASMIN 기반 상위 FSM(B0) + BehaviorTree.CPP v4 기반 상태별 BT 실행기(B1)"** 였다.
YASMIN 2상태 PoC 를 게이트로 두는 계획까지 있었다. 실제 구현은 **둘 다 쓰지 않았다.**

| 항목 | 조사 결론 (2026-06-29) | 실제 구현 |
|---|---|---|
| B0 상위 FSM | **YASMIN** (ROS 2 네이티브 FSM, 웹 뷰어) | 자체 순수 Python FSM (`patrol_planner.py`, `state_machine.py`) |
| B1 BT 실행기 | **BehaviorTree.CPP v4** + ROS 2 action 래퍼 리프 | 미구현. 주행 임무는 Nav2 `bt_navigator` 에 위임 |
| 통합 행동코어 노드 | 상위 FSM 이 상태별 BT 를 로드 / halt | 없음. 기능별 상태기계가 분산 |

저장소 코드에 `yasmin` · `behaviortree` · `py_trees` 의존성이 **전혀 없다**(전수 grep 0건).

> **아래 표는 사후 정리다.** 조사 결론을 뒤집은 시점의 판단 근거가 문서로 남아 있지 않다.
> "왜 안 썼는가"를 기록한 워크로그도 스펙도 저장소에 없다.
> 따라서 다음은 현재 코드와 측정치에서 역으로 재구성한 것이며, **당시의 실제 의사결정 기록이 아니다.**

| 사후 정리한 이유 | 내용 |
|---|---|
| **Nav2가 이미 BT다** | 주행 임무의 재계획 · 복구(`navigate_to_pose_w_replanning_and_recovery`)는 이미 검증된 BT 로 돌고 있다. 그 위에 우리 BT 를 한 겹 더 얹으면 복구 로직이 **두 곳**에 생긴다 |
| **상태 수가 적다** | 순찰 3상태, 도킹 8상태(+`ESTOP`). 전이표가 폭발하는 규모가 아니다. BT 의 이점(복잡한 임무의 모듈화)이 발현되는 크기가 아직 아니다 |
| **CPU 예산** | RPi 4 에서 idle 여유 20% 가 완주 임계였다. 실행기를 하나 더 얹을 여유가 없었다 |
| **검증 비용** | Jazzy 에서 BehaviorTree.ROS2 빌드 · 배포 안정성 검증이 PoC 게이트였는데, 그 시간을 통행 중재 · 긴급정지 같은 **실기 필수 기능**에 썼다 |

첫 항목이 §1 마지막에 남겨둔 복선이다. **"BT 를 쓰자"는 결론은 이미 절반 실현돼 있었다.**
Nav2 를 액션으로 호출하는 순간 우리는 남이 만든 BT 위에서 돌고 있었고,
그 위에 자체 실행기를 얹는 일은 새 능력이 아니라 **중복 계층**을 만드는 일이었다.

그렇다고 이 정리가 당시의 판단을 증명하지는 않는다. 지금 남은 사실은 두 개뿐이다 —
조사 결론이 있었고, 코드에는 없다. 그 사이를 메우는 문서가 없다.
**발표에서 "설계대로 구현했다"고 말하지 않는 편이 정확하다.**

## 9. 설계 원칙으로 남은 것

계층 구성은 바뀌었지만, 두 FSM 을 만들면서 반복해서 쓴 규칙은 남았다.

| 원칙 | 어디에 | 왜 |
|---|---|---|
| **순수 함수 로직 분리** | FSM = `patrol_planner.py` · `state_machine.py`, 규칙 엔진 = `traffic_rules.py`, 파서 = `estop.py` · `commands.py` | ROS · 로봇 없이 전이표와 판정 규칙을 전량 테스트. 실기 시간이 비싸므로 논리 오류는 지상에서 잡는다 |
| **히스테리시스** | YIELD 진입 `yield_radius` / 해제 `clear_radius` (해제 반경이 더 큼) | 경계에서 상태가 떨리는 것을 막는다. 생성자에서 `clear ≥ yield` 강제 |
| **fail-closed / fail-open 구분** | 순찰 = 승인 없으면 정지 / 도킹 = 중재기 없어도 진행 | 순찰은 멈춰도 안전하지만, 정밀주차 중단은 오히려 위험하다 |
| **타임아웃 → pause + 알림** | `YIELD_TIMEOUT_S`, `EDGE_WAIT_TIMEOUT_S`, goal 무응답 20초 | 무한 대기 대신 사람에게 넘긴다. **조용한 정지가 가장 나쁘다** |
| **재시도 백오프** | Nav2 goal reject/abort 시 `GOAL_RETRY_BACKOFF_S = 2.0` | 즉시 재시도는 같은 실패를 반복하며 CPU 만 먹는다 |
| **엄격 파서 + 관대한 파서 분리** | `parse_estop`(넓게 정지) / `parse_estop_msg`(엄격, 실패 시 `None`) | 정지는 넓게 받고, 해제는 손상 메시지로 오해제되지 않게 |
| **워치독(자기 감시)** | `OWN_HB_TIMEOUT_S = 8.0` | 관제가 못 보는 로봇은 스스로 주행하지 않는다 |

마지막 워치독은 통행 중재기와 짝을 이룬다. 중재기는 15초 무수신이면 그 로봇의 점유를 지우는데,
지워진 뒤에도 로봇이 계속 달리면 **중재기 눈에 없는 로봇이 통로를 점유**하는 상태가 된다.
그래서 순찰 노드가 자기 heartbeat 를 구독해 **8초**에 먼저 멈춘다. 임계를 15초보다 작게 잡은 것이 전부다.
