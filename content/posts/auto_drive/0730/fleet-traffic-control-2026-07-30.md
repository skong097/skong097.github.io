## 0. 요약

로봇 두 대가 같은 순찰 링을 돌면 부딪힌다. 중앙 관제가 **구간 사용 허가**를 내주는 방식으로 풀었다.

- **표준에서 빌린 것**: VDA 5050 3.0 의 **응답 상태 모델**, Open-RMF 의 **제어 수준 구분**,
  최신 Lifelong MAPF 연구의 **실행 감시 원칙**. 딱 세 가지만.
- **안 가져온 것**: Open-RMF 스택 전체, VDA 5050 전체 프로토콜, 범용 MAPF planner, 학습 기반 제어.
  로봇 2~3대·노드 5개 규모에 도입 비용이 이익보다 크다.
- **우리 맵이 가르쳐 준 것**: 교과서적 그래프 예약이 **불균등한 실제 좌표**에서 어떻게 깨지는지.
  같은 규칙이 실기에서 충돌 3건을 냈고, 원인이 셋 다 달랐다.

핵심 성과는 알고리즘이 아니라 **실측으로 규칙을 확정한 과정**이다.

## 1. 문제 — 이 규모에서는 교과서가 안 맞는다

```
아레나      2.10 × 1.24 m
로봇 폭     0.2 m          두 로봇 중심 간 최소 간격 0.2 m
순찰 링     노드 5개(AprilTag 4 + 남쪽 경유점 1)
```

링 간선 길이가 **3배까지 차이 난다.**

| 구간 | 길이 |
|---|---:|
| tag7 → tag8 | 0.489 m |
| S → tag9 | 0.648 m |
| tag9 → tag10 | 0.648 m |
| tag8 → S | 0.814 m |
| **tag10 → tag7** | **1.437 m** |

창고형 MAPF 연구가 전제하는 **균일 격자**와 정반대다. 게다가 남쪽 경유점 S 가 아레나 한가운데
있어 어느 지점에서든 가깝다. 이 두 가지가 뒤에서 실제 결함으로 이어진다(§4).

## 2. 참고한 표준과 연구

> **출처에 대한 정직한 고지.** 아래 논문들은 사내 조사 문서
> (`scripts/2026-07-29-fleet-technology-research.md`)의 요약을 통해 참조했고, 원문을 직접
> 읽고 수치를 검증하지는 않았다. 일부는 프리프린트다. 본 설계가 **논문의 실험 수치에 의존하는
> 부분은 없다** — 채택한 것은 상태 모델(표준)과 설계 원칙뿐이다.

### 2-1. VDA 5050 3.0.0 — 채택 (상태 모델)

VDA·VDMA 가 2026-03 공개한 중앙 관제 ↔ 이기종 모바일 로봇 통신 표준. 주문 단위가
**node / edge / action** 이다.

★**정정(원문 확인 후).** 초판에서 이 상태 모델을 "corridor 사용 승인" 이라고 적었는데 틀렸다.
명세에서 `GRANTED / QUEUED / REJECTED / REVOKED` 는 **zone request 의 `responseType`** 이다.
corridor 는 별개 개념으로, 엣지의 선택적 속성(`releaseRequired`, `corridorReferencePoint`)이다.
사내 조사 문서의 요약을 검증 없이 옮긴 결과였다.

```
로봇 → 관제   state 토픽의 zoneRequests 배열
              {requestId, requestType, zoneSetId, zoneId, requestStatus, trajectory?}
              requestType = ACCESS ('RELEASE' 존 진입 전) | REPLANNING (궤적 후보 제안)
관제 → 로봇   responses 토픽. requestId 로 짝을 맞춘다

responseType    GRANTED   진입·궤적 사용 허가. leaseExpiry 를 함께 줄 수 있다
                QUEUED    접수했으나 허가는 아니다 — 대기
                REJECTED  진입 금지. 존 밖에 머문다
                REVOKED   준 허가를 회수. 요청을 state 에서 지우고 진입하지 않는다
requestStatus   REQUESTED / GRANTED / QUEUED / REVOKED / EXPIRED
                ★EXPIRED = leaseExpiry 경과. 관제가 갱신 응답을 보내면 연장된다
```

**우리가 가져온 것은 응답 상태 모델 하나다.** MQTT·factsheet·전체 프로토콜은 안 가져왔다.
`EXPIRED` 도 안 넣었다 — lease 자체를 도입하지 않았기 때문이다.

이걸 가져온 이유가 있다. 초기 구현은 승인 여부를 **불리언**으로 돌려줬는데, 같은 결함이 **네 번**
재발했다.

```
불리언 False → 응답 메시지가 아예 안 나감
             → 요청자가 "거부"와 "중재기 사망"을 구별 못 함
             → 3초 fail-open 으로 빠져 무중재 주행
  ① 목적지 변경 거부가 무중재 도킹으로 이어짐
  ② 재시작한 요청자가 조용히 영구 거부됨
  ③ 거부 사유 4종을 노드가 한 덩어리로 보고 무조건 승인
  ④ 응답 중복 억제가 재시작 요청자를 침묵시킴
```

표준이 이미 정해 둔 것을 네 번에 걸쳐 재발견한 셈이다. 상태를 명시하고 **모든 요청에 반드시
응답**하도록 바꾸자 이 계열이 사라졌다. 침묵은 이제 "중재기가 죽었다" 한 가지만 뜻한다.

★**`REVOKED` 와 lease 는 일부러 안 넣었다.** 승인 후 그 로봇을 원격으로 멈출 수단이 없다.
회수할 수 없는데 회수 상태를 두면 **잘못된 안전감**만 준다.

### 2-1-A. ★우리가 안 본 메커니즘 — base / horizon

VDA 5050 의 **주** 교통 제어는 zone request 가 아니라 주문의 **release 플래그**다.

```
관제가 전체 계획 경로를 보낸다. 각 노드·엣지에 released: true/false
  base            released:true  — 로봇이 주행해도 되는 구간
  horizon         released:false — 계획은 됐지만 아직 허가 안 된 구간
  decision point  base 의 마지막 노드. 로봇은 여기서 멈춘다
관제는 로봇이 decision point 에 닿기 전에 orderUpdateId 를 올려 base 를 연장한다
```

**우리 방식과 방향이 반대다.** 우리는 로봇이 묻고 관제가 답하는데, VDA 5050 은 관제가 미리 밀어준다.

그리고 명세에 이런 제약이 있다.

> "An edge can be released only if **both the start and the end node** of the edge are released."

**오늘 tag10 추돌 후 확정한 "엣지 위에서는 양끝 노드를 모두 잠근다"(§4-3)와 같은 규칙이다.**
우리는 이것을 로봇을 부딪혀 가며 다시 발견했다. 또 하나 —

> "After an unreleased edge, no released nodes or edges can follow in the sequence."

**건너뛰기 폐기(§4-4)와 같은 취지다.** 허가 안 된 구간 뒤의 것을 미리 쓰면 안 된다.

세대 관리도 참고할 만하다. VDA 5050 은 주문 세대를 **`orderUpdateId`** 로 관리하고 로봇이
새 업데이트의 첫 노드가 자기 decision point 와 맞는지 검증한다. 우리의 미해결 항목인
`stale_seq` 잠금(§5-5)이 바로 이 세대 관리를 안 해서 생긴 문제다.

### 2-2. Open-RMF — 개념만 채택 (제어 수준 구분)

ROS 2 기반 multi-fleet 통합 플랫폼. 도입은 하지 않았다(건물 규모·이종 함대·엘리베이터 연동 전제).
다만 연동 수준 구분이 우리 설계를 정직하게 만들었다.

| Open-RMF 수준 | 우리 대응 |
|---|---|
| **Full control** — 경로 실행을 세밀히 제어 | **순찰**: 인접 구간마다 승인을 받는다 |
| **Read only** — 예상 경로 제출, 관측만 | **도킹**: 명령 발행 후 Nav2 에 개입 못 한다 |

**두 동작을 같은 안전 보장으로 표현하면 안 된다**는 것이 핵심이다. 그래서 문서 첫머리에
보장 범위를 명시했다 — *"순찰의 인접 구간 이동만 승인 단위로 제어한다. 도킹은 출발 시점만
제어하고 주행 중에는 제어하지 않는다."*

### 2-3. Lifelong MAPF — 원칙만 채택 (실행 감시)

| 연구 | 내용 | 채택 |
|---|---|---|
| Zahrádka et al. 2025, [arXiv:2509.10284](https://arxiv.org/abs/2509.10284) | Action Dependency Graph 로 실행을 감시, 누적 지연 시에만 재계획 | **원칙만** |
| Yan et al. 2025, [arXiv:2511.21886](https://arxiv.org/abs/2511.21886) | 동역학·통신 지연·controller 편차를 반영한 실행시간 예측 | **원칙만** |
| Yan et al. 2026, [arXiv:2602.15721](https://arxiv.org/abs/2602.15721) | Lifelong MAPF 평가에 빠지면 안 되는 현실 요소 정리 | **원칙만** |
| Tang et al. 2025, [arXiv:2501.02803](https://arxiv.org/abs/2501.02803) | cache 기반 Lifelong MAPF | 미채택 |
| Combrink et al. 2025, [arXiv:2503.13175](https://arxiv.org/abs/2503.13175) | 연속시간·로봇 부피 반영 | 미채택 |
| Jiang et al. 2024, [arXiv:2410.21415](https://arxiv.org/abs/2410.21415) | 모방학습, 1만 agent 규모 | 미채택 |

이 계열이 공통으로 말하는 것은 **더 좋은 planner 가 아니라 실행 상태 기계와 관측성**이다.
우리 규모에는 새 planner 가 필요 없고, 그래서 채택한 것도 planner 가 아니라 **로그 한 줄**이다.

```
rid=44 seq=7 REQUEST  kind=patrol from=4 to=0
rid=44 seq=7 QUEUED   reason=moving blocker=50
rid=44 seq=7 GRANTED  edge=(0,4)
rid=87 STALE     heartbeat 5s 무수신 — 점유 유지
```

**사고가 나면 이 로그만으로 시점을 복원할 수 있어야 한다.** 실제로 오늘 충돌 3건의 원인을
전부 이 로그로 분해했다(§4).

시간 예약(interval reservation)은 도입하지 않았다. 실주행 시간 편차가 커서 부정확한 시간표보다
**"승인 후 점유, 도착 후 원자적 전환"** 이 더 안전하고 단순하다.

## 3. 적용한 기술

### 3-1. 구조 — 전부 PC, 로봇 무접촉

```
웹앱 / 콘솔 / 순찰노드 ──(요청)──▶  중재 노드(PC, 도메인50)  ──(승인)──▶ 요청자
                                        ▲                          └─▶ /robot_<id>/dock_cmd
       로봇 agent ──(heartbeat 2Hz)─────┘
```

로봇에 올라가는 코드는 **0줄**이다. RPi4 함대에서 도킹 성패의 임계가 **CPU 여유 20%** 라는
직전 측정 결과가 있어(2026-07-29), 중재 부담을 로봇에 분산하지 않고 PC 한 곳에 모았다.
새 토픽은 2개(`/traffic/request`, `/traffic/grant`)뿐이고 나머지는 이미 흐르던 것을 구독만 한다.

### 3-2. 점유 — pose 에서 유도한다

누적 장부를 두지 않는다. heartbeat 한 번에 그 로봇의 점유를 **통째로 다시 계산**한다.
해제를 잊어 유령 점유가 남는 실수가 구조적으로 불가능해진다.

```
최근접 노드까지 ≤ 0.15 m            →  그 노드 1개
링 선분에 투영해 t 가 0·1 로 클램프  →  그 끝점 노드 1개    (노드를 지나 링 밖)
선분 위(0 < t < 1)                  →  양끝 노드 + 그 엣지
+ 승인받았으면 목표 노드도 점유       →  아직 안 움직인 사이를 메운다. 도착하면 소멸
```

**순찰·도킹·정지를 구분하지 않는다.** heartbeat 를 내면 항상 무언가를 점유한다.
초기 설계는 "도킹 중인 로봇만 선점을 만든다" 였는데, 그러면 **정지한 로봇이 순찰 입장에서
투명**해져 실제로 들이받은 적이 있다(2026-07-28).

★**heartbeat 가 끊겨도 점유를 자동 해제하지 않는다.** 통신이 끊긴 로봇은 물리적으로는 그 자리에
있다. 푸는 순간 그쪽으로 다른 로봇을 보내게 된다.

### 3-3. 승인 — 모아서 한 번에 판정

```
요청 도착  →  pending 에 넣기만 (즉시 승인하지 않는다)
tick(5Hz)  →  pending 을 우선순위로 정렬 → 충돌 없는 것부터 승인
판정        →  엣지 {a,b} 와 도착 노드 b 가 자기 것 말고 비어 있으면 승인
```

즉시 승인하면 먼저 도착한 요청이 이미 출발해버려 우선순위를 적용할 자리가 없다.
`reason` 판정은 **pass 가 끝난 뒤** 최종 점유 상태로 한다 — 나눠주는 도중에 판정하면
"아직 판정 안 된 로봇"의 취급이 판정 순서에 좌우된다.

**우선순위**(순수 함수 하나, 동시 요청 경합과 거리 yield 비대칭화에 같이 쓴다):

```
1. 배터리 < 7.0 V 인 쪽이 한쪽뿐이면        → 그 로봇
2. 화재 이벤트가 활성이면 zone 중심에 가까운 쪽
3. 그 외                                    → id 낮은 쪽
```

### 3-4. 고장 시 동작

```
중재 노드 무응답   순찰 → 노드에서 정지(fail-closed, 멈춰도 잃는 것 없음)
                   도킹 → 3초 후 직접 발행 + "충돌 제어 미동작" 경고 배너(가용성 우선)
기동 직후 3초      승인하지 않는다 — 재시작 시 점유표가 비어 아무나 승인하는 구멍
대기 20초 초과     pause + 운영자 알림
```

★경고가 조용하면 fail-open 과 같다. 방어가 꺼진 줄 모르고 실기를 진행해 충돌한 전례가 있다.

## 4. 우리 맵에서의 검증

### 4-1. 실기 전 — 띄워봐야만 나오는 결함

단위 테스트 96개가 통과한 상태에서 중재 노드를 처음 기동하자 바로 나왔다.

```
New publisher discovered on topic '/robots/heartbeat',
offering incompatible QoS. No messages will be received from it.
Last incompatible policy: RELIABILITY
```

agent 는 heartbeat 를 **BEST_EFFORT** 로 주기 발행하는데 중재 노드가 기본값(RELIABLE)로
구독해 **한 건도 받지 못했다.** 점유표가 영원히 비므로 유예 3초 후 **아무나 승인**한다.
같은 프로젝트의 `patrol_node` 와 웹앱은 이미 BEST_EFFORT 로 맞춰져 있었고 중재 노드만 빠져 있었다.

**교훈: 단위 테스트로는 잡히지 않는 계층이 있다.**

수정 후 실물 2대로 즉시 재검증했다.

```
로봇44 tag7(0.142m) · 로봇87 tag8(0.032m) 정지 상태
요청  {"rid":44,"kind":"patrol","from_node":4,"to_node":0}
응답  {"status":"QUEUED","reason":"static","blocker":87}
      점유 반영 ✅  정지 판정 ✅  막은 로봇 지목 ✅
```

### 4-2. 결함 ① — 링 밖에 선 로봇이 0.9 m 떨어진 노드를 잠갔다

로봇50 이 tag9 **바깥** 0.244 m 에 정지해 있는데, 0.892 m 떨어진 S 까지 점유로 잡혔다.
계산해 보니 원인이 명확했다.

| 링 선분 | 거리 | 투영 t |
|---|---:|---:|
| S → tag9 | **0.2444 m** | 1.00 (끝점 클램프) |
| tag9 → tag10 | **0.2444 m** | 0.00 (끝점 클램프) |
| tag10 → tag7 | 0.7196 m | 0.00 |

두 선분 거리가 **완전히 같다.** 둘 다 "가장 가까운 점 = tag9" 이기 때문이다. 코드는 먼저 오는
`S-tag9` 를 고르고 그 **양끝**을 잠갔다.

투영이 끝점에 클램프됐다는 건 **그 선분 위가 아니라 그 노드 옆**이라는 뜻인데 구분하지 않았다.
→ `t` 가 0·1 이면 그 노드 하나만 점유.

★이 결함은 **사용자의 물리적 직관**이 먼저 잡았다 — *"tag9 에 바짝 붙어 있는데 S 를 점유한다는 게
말이 안 되지."* 코드가 아니라 현장이 맞았다.

### 4-3. 결함 ② — 처리량을 얻으려다 안전을 깎았다

엣지 위에서 **가까운 끝점 하나만** 잠그도록 바꿨다. 측정상 개선이 뚜렷했다.

| 구간 | 잠기는 노드 수 (변경 전) | (변경 후) |
|---|---:|---:|
| tag10 → tag7 | 1.79 | 1.00 |
| tag8 → S | 1.68 | 1.00 |
| 나머지 3개 | 1.37 ~ 1.58 | 1.00 |

**그리고 그날 tag10 에서 추돌했다.**

```
앞차가 tag10→tag7(1.437 m) 중간을 넘는 순간   점유가 tag10 → tag7 로 전환 = tag10 이 열림
뒤차가 즉시 tag10 을 승인받고 진입
그 시점 간격 ≈ 0.7 m → 앞차가 감속·회전하면 추돌
```

로그에 그대로 남았다.

```
44 seq=11  GRANTED edge=(3,4)        44 가 tag10→tag7 진입
50 seq=1   QUEUED  moving blocker=44
50 seq=1   GRANTED edge=(2,3)        44 가 중간 넘자 tag10 열려서 50 진입
```

**인접한 두 엣지는 노드를 공유한다.** 그 공유 노드가 열리면 두 로봇이 거기서 만난다.
반면 인접하지 않은 엣지끼리는 실측상 **0.486 m 이상** 떨어져 있어 위험하지 않다.

| 엣지 쌍 (비인접) | 최단 거리 |
|---|---:|
| tag8-S vs tag10-tag7 | 0.486 m |
| S-tag9 vs tag10-tag7 | 0.490 m |
| tag8-S vs tag9-tag10 | 0.639 m |
| S-tag9 vs tag7-tag8 | 0.809 m |
| tag9-tag10 vs tag7-tag8 | 1.433 m |

→ **양끝 + 엣지를 모두 잠근다. 과잉 점유는 감수한다.**

### 4-4. 결함 ③ — 건너뛰기가 링에 없는 대각선을 만들었다

주차한 로봇이 링 노드를 영구 점유하면 순찰이 죽는다. 그래서 "막은 로봇이 정지 상태면 그 노드를
건너뛴다" 를 넣었다. 그런데 건너뛰기는 인덱스를 2 전진시키므로 **tag7 → S**, **S → tag10** 같은
**링에 없는 대각선**을 주행하게 된다. 그 구간은 요청도 승인도 이벤트도 없다.

로그 지문이 명확하다 — 같은 로봇의 다음 `REQUEST` 의 `from` 이 이전 `to` 와 이어지지 않는다.

```
seq=1  0→1  GRANTED                       tag8 → S
seq=2  1→2  QUEUED static blocker=50      S → tag9 막힘
seq=3  3→4  GRANTED                       ★from 이 3. 그 사이 S→tag10 을 대각선으로 갔다
```

한 세션에 3번 이 대각선을 탔고 아레나 중앙에서 충돌했다.
→ **QUEUED 는 사유 무관 대기. 건너뛰기 폐기.**

대가는 명확하다. 충전·주차한 로봇이 링 위에 있으면 순찰이 그 앞에서 멈춘다.
**받아들이기로 했다** — 중재기가 모르는 주행 구간을 남기는 것보다 낫다.

### 4-5. 대기 시간 — 규칙이 아니라 배치 문제였다

"대기가 너무 길다" 는 지적에, 실제 `Arbiter` 에 로봇을 태워 180초 시뮬레이션했다.

| 속도 | 배치 | 총 홉 | 최대 대기 | 대기 비율 |
|---|---|---:|---:|---:|
| 0.06 m/s | 인접 (tag9·tag10) | 23 | **21.6 s** | 6% |
| 0.06 m/s | 2노드 간격 | 26 | 8.2 s | 2% |
| 0.06 m/s | 반대편 | 25 | **0.4 s** | 0% |
| 0.15 m/s | 인접 | 63 | 8.6 s | 2% |
| 0.15 m/s | 반대편 | 65 | 0.0 s | 0% |

**같은 규칙인데 배치만 바꿔도 21.6초 → 0.4초다.** 규칙을 느슨하게 할 문제가 아니었다.

로봇 수별 최대 정상 대기(0.06 m/s):

```
2대 8.2 s(간격)  ·  3대 21.6 s  ·  4대 38.4 s      교착(굶음)은 어느 경우에도 없음
```

→ 중재 대기 타임아웃을 **20초**로 두되, **3대 이상 투입 시 40초로 올린다**.
Nav2 무응답·거리 yield 감시는 20초 그대로 둔다 — 길게 잡으면 진짜 고장을 늦게 안다.

### 4-5-A. 그래서 어디에 세우고 시작할 것인가 — 우리 맵 배치표

뒤차는 앞차가 다음 노드에 닿는 순간 들어오므로 **로봇 간 간격 ≈ 노드 간 거리**가 된다.
따라서 노드를 촘촘히 할수록 바짝 붙는다 — 다만 **어느 엣지를 쪼개느냐**로 결과가 갈린다.

**모든 엣지를 균일하게 쪼개면 안 된다.** 최단 엣지가 같이 짧아져 간격의 하한이 무너진다.

| 구성 | 노드 수 | 최단 엣지 | 최대 대기 | 두 로봇 최소 간격 |
|---|---:|---:|---:|---:|
| 현재 | 5 | 0.489 m | 5.8 s | 0.489 m |
| 0.7 m 초과 분할 | 9 | 0.359 m | 5.8 s | **0.361 m** |
| 0.35 m 초과 분할 | 18 | 0.180 m | 2.2 s | **0.252 m** |

로봇 폭이 0.2 m 이므로 간격 0.36 m 면 사이가 16 cm 다. 대기는 거의 안 줄고 위험만 커진다.

**★그러나 긴 엣지 하나만 쪼개는 것은 다르다 (미적용 · 다음 과제)**

`tag10 → tag7` 은 1.437 m 로 최단 엣지의 3배다. 이것만 중점에서 2등분하면
최단 엣지(0.489 m)를 건드리지 않으므로 **간격 하한이 그대로 유지되면서 대기만 줄어든다.**

| 배치 | 현재 5노드 | 긴 엣지만 분할 6노드 |
|---|---|---|
| 인접 tag9+tag10 | 21.6 s · 23홉 · 간격 0.489 m | **9.6 s · 29홉 · 간격 0.488 m** |
| 3대 tag8+S+tag10 | 13.4 s · 26홉 · 간격 0.488 m | **8.4 s · 45홉 · 간격 0.488 m** |
| 반대편 tag9+tag7 | 0.0 s · 27홉 | 0.0 s · 32홉 |

**대기 −56% / 홉 +26~73% / 안전 간격 불변.** 판단 기준은 하나다 —
**최단 엣지 0.489 m 아래로 내려가는 분할은 하지 않는다.**

```
쪼갤 수 있는 것
  tag10-tag7  1.437m → 0.72m × 2     ✅  (3등분 0.48m 는 하한에 걸려 불가)
  tag8-S      0.814m → 0.41m × 2     ❌  하한 밑
  나머지 3개  0.489~0.648m           —   이미 하한
```

즉 우리 맵에서 쪼갤 수 있는 것은 **`tag10-tag7` 하나뿐**이다.

**★그런데 맵을 열어 보니 분할 지점이 하나로 좁혀졌다.** `wasab_map11.pgm` 에서
`inflation_radius = 0.12 m` 기준으로 각 후보의 벽까지 여유를 쟀다.

| 후보 | 벽까지 여유 | 판정 |
|---|---:|---|
| **(0.85, 0.66)** | **0.180 m** | ✅ 유효. 기존 tag8·tag9(0.120 m)보다 여유가 크다 |
| (0.7245, 0.597) — 직선 중점 | 0.152 m | 지점 자체는 OK, 그러나 아래 참조 |
| (0.60, 0.64) | 0.102 m | ❌ inflation 미달 |
| (0.38, 0.62) | 0.060 m | ❌ inflation 미달 |

`(0.85, 0.66)` 을 넣으면 엣지가 **0.590 m + 0.853 m** 로 나뉜다. 균등 2등분은 아니지만
둘 다 최단 엣지 0.489 m 보다 길어 하한을 지킨다.

`tag_nodes` 인덱스 재매핑(`8:0, 9:2, 10:3, 7:5`)이 필요하고, 실주행 확인은 아직 안 했다.

### 4-5-B. ★맵을 재고 알게 된 것 — 엣지는 직선이 아니다

`tag10 → tag7` **직선은 벽을 통과한다.**

```
직선 구간 21등분, 벽까지 여유
  t=0.00  0.180m ████████
  t=0.50  0.152m ███████        ← 직선 중점
  t=0.60  0.040m ██
  t=0.75  0.000m                ★벽
  t=0.80  0.000m                ★벽
  t=1.00  0.120m ██████
```

프론트의 `PATROL_PATH` 가 우회점 `(0.85,0.66)`·`(0.38,0.62)` 를 넣어 둔 이유가 이것이다.
그 실제 경로도 최저 여유가 **0.040 m** 인 구간을 지난다(`(0.343, 0.611)`).

**우리 점유 모델은 엣지를 직선 선분으로 계산한다.** 즉 잠그는 선과 로봇이 실제로 지나는 선이
다르다. 링이 짧고 통로가 좁아 지금까지는 결과가 같았지만, 원리상 어긋난다.

★2026-07-30 실기에서 관측한 **"Nav2 가 승인 레인을 0.4 m 벗어났다"** 도 이것과 무관하지 않을 수
있다. 승인은 직선 기준으로 나가는데 Nav2 는 벽을 피해 도는 경로를 계획하기 때문이다.
(둘의 인과는 미확인 — 추정이다.)

당장의 실질적인 레버는 **시작 배치**다. 링 둘레 4.036 m, 노드가 고르지 않게 박혀 있다.

### 4-6. 최종 확인 — 2대 정상 순환

```
44   0→1 → 1→2 → 2→3 → 3→4 → 4→0 → 0→1 → 1→2      끊김 없음
50   3→4 → 4→0 → 0→1 → 1→2 → 2→3 → 3→4            〃
건너뛰기 0회 · pause 0건 · 충돌 0건
```

규칙이 실제로 막아 준 장면:

```
rid=44 seq=3  QUEUED  reason=static  blocker=50     50 이 tag10 에 정지
rid=50 seq=1  REQUEST from=3 to=4                   50 이 출발
rid=44 seq=3  QUEUED  reason=moving blocker=50      이동 중이라 여전히 대기
rid=50 seq=1  GRANTED edge=(3,4)
rid=44 seq=3  GRANTED edge=(2,3)                    50 이 tag7 도착하자 tag10 열림
```

**오전에 추돌났던 바로 그 지점**에서, 이번엔 양끝 잠금이 뒤차를 붙지 못하게 막았다.

### 4-7. 그리고 규칙 밖의 충돌 하나

마지막 충돌은 잠금 규칙 문제가 아니었다.

```
44 가 승인받은 것   edge=(1,2)  S→tag9   (남쪽 통로)
44 의 실제 위치     (1.211, 0.790)        tag10 근처, 북쪽
```

44 의 재측위가 실패한 뒤 복구되지 않아 **AMCL 이 틀린 위치를 믿고 있었다.** 그러면 그 아래가
전부 어긋난다 — 순찰 노드는 "S 도착" 으로 판단해 `from=1` 로 요청하고, 중재기는 그 주장을 믿고
승인하고, Nav2 는 틀린 pose 로 주행한다.

★**중재기는 먹인 좌표만큼만 정확하다. 측위가 깨진 로봇에는 어떤 잠금 규칙도 소용없다.**

## 5. 한계 (정직하게)

1. **출발 전 게이트일 뿐이다.** 이미 진입한 로봇은 이 설계로 못 뺀다. 진입 후 방어는
   비대칭 거리 yield 와 각 로봇 Nav2 의 라이다 costmap 이다.
2. **선점은 규약이지 물리적 보장이 아니다.** Nav2 는 자기 경로를 계획하므로 승인받은 레인을
   벗어날 수 있다 — 실제로 관측됐다(승인 구간에서 0.4 m 벗어남).
3. **도킹은 주행 중 제어되지 않는다.** 출발 시점만 승인하고, 그 뒤 Nav2 자율 주행 구간은
   개입 지점이 없다. 다만 heartbeat 점유로 계속 관측되므로 순찰은 회피한다.
4. **중재 노드는 단일 장애점**이다. 순찰은 멈추고 도킹은 fail-open 으로 빠진다(의도된 선택).
5. **stale 상태가 재기동을 막는다(미해결).** 승인 못 받고 끝난 pending 이 남아, 순찰 노드를
   재기동하면 `REJECTED reason=stale_seq` 로 영구 거부된다. 현재는 중재 노드 재기동으로 푼다.
   맵에서 뺀 로봇의 유령 점유도 같은 뿌리다.
6. **과잉 점유를 감수한다.** 긴 엣지(1.437 m)에 로봇이 들어가면 사실상 링 절반이 잠긴다.
7. ★**엣지를 직선으로 모델링한다(§4-5-B).** `tag10→tag7` 직선은 실제로 벽을 통과한다.
   잠그는 선과 로봇이 지나는 선이 다르므로, 링이 커지거나 통로가 넓어지면 어긋남이 드러난다.

## 6. 이 작업에서 남길 만한 것

- **표준을 먼저 읽었으면 네 번 안 틀렸다.** 불리언으로 여러 상태를 표현해 같은 결함이 네 번
  재발했고, VDA 5050 은 그 답을 이미 정의해 두고 있었다.
- **테스트 픽스처가 실제 배치와 다르면 결함을 구조적으로 은폐한다.** 4노드 정사각형 픽스처가
  불균등 5노드 링의 기하 오류를 통째로 가렸다. 실좌표로 도는 회귀 테스트를 넣어 막았다.
- **처리량을 얻으려고 안전을 깎지 말 것.** 엣지 한쪽만 잠그는 변경이 곧바로 추돌을 냈다.
- **대기가 길면 규칙이 아니라 배치를 의심할 것.** 같은 규칙에서 21.6초 vs 0.4초.
- **띄워보지 않은 코드는 검증된 게 아니다.** 단위 테스트 96개를 통과한 코드가 실행 즉시
  QoS 불일치로 아무것도 못 받고 있었다.
