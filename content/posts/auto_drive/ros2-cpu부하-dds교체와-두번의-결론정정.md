자율주행 로봇이 **가만히 서 있는데도** 4코어 라즈베리파이 CPU의 60% 이상이 사라지고 있었다.
순찰이나 도킹 같은 임무가 추가로 쓰는 건 겨우 +10~27%p — 즉 부하의 본체는
**"스택이 떠 있다는 사실 자체"** 였다.

이 글은 그 상시 부하를 걷어내려고 로봇 4대를 실측한 기록이다. 두 개의 레버를 각각
A/B로 검증했다.

| # | 튜닝 포인트 | 결과 | 위험 |
|---|---|---|---|
| **①** | **미들웨어 교체** Fast DDS → Cyclone DDS | 순찰 구간 **−34.19%p**(−12.6%) | 중 — 전 노드 동시 전환 필요 |
| **②** | **중복 `joint_state_publisher` 제거** | **−19.01%p**, 실기 검증 완료 | **없음** |

그런데 이 글의 진짜 내용은 튜닝 수치가 아니다. 측정 대상을 1대에서 4대로 늘리는 동안
**내가 내린 결론이 두 번 뒤집혔다**는 쪽이다.

- 3번째 로봇(31)을 재보니 CPU가 3분의 1로 나왔다 → "**보드 세대가 전부다**"
- 4번째 로봇(87)이 같은 구형 보드로 도킹을 완주했다 → "**보드가 아니라 CPU 여유였다**"

측정 대상 · 조건은 이렇다.

| 항목 | 내용 |
|---|---|
| 실측일 | 2026-07-29 |
| 대상 | 자율주행 로봇 4대 — **RPi4**(로봇44·50·87) / **RPi5**(로봇31), 각 4코어 aarch64 |
| 소프트웨어 | ROS 2 Jazzy · Nav2 · AMCL · AprilTag 정밀 도킹 |

이 로봇들이 무엇을 하는 물건인지는 앞선 글
[로봇 함대를 한 화면에서](../wasab-로봇함대-두-도메인을-잇는-agent와-cpu튜닝/)에 적어 두었다.

## 1. 배경 — ROS 2에서 DDS란 무엇인가

### 1-1. ROS 1과 결정적으로 다른 점

ROS 1은 중앙 `roscore`(마스터)가 노드들을 중개했다. 마스터가 죽으면 전체가 멈추고,
실시간성·보안 보장이 없었다. **ROS 2는 마스터를 없애고 그 자리에 산업 표준 통신
미들웨어인 DDS(Data Distribution Service)를 넣었다.**

{{< figure src="/images/diagrams/autodrive-dds-ros1-vs-ros2.svg" alt="ROS 1과 ROS 2의 통신 구조 비교. ROS 1은 노드가 중앙 roscore 마스터를 거쳐 다른 노드와 통신해 마스터가 죽으면 전체가 멈추는 단일 실패점이 되고, ROS 2는 마스터를 없애고 그 자리에 DDS 분산 디스커버리를 넣어 노드끼리 양방향 P2P로 직접 통신한다." caption="ROS 2에는 마스터가 없다 — 그 자리를 DDS가 채운다" >}}

DDS는 OMG(Object Management Group)가 표준화한 **발행-구독 미들웨어**로, 항공·국방·금융
등에서 쓰이던 기술이다. ROS 2는 이를 `rmw`(ROS MiddleWare) 추상 계층으로 감쌌다.

### 1-2. 계층 구조 — 이 실험이 성립하는 이유

{{< figure src="/images/diagrams/autodrive-dds-rmw-stack.svg" alt="ROS 2의 미들웨어 계층 구조. 위에서부터 애플리케이션의 내 노드, 클라이언트 라이브러리 rcl, 추상 계층 rmw, DDS 구현체 Fast DDS와 Cyclone DDS와 Connext, 전송 계층의 UDP와 TCP와 공유메모리 순으로 쌓이며, rmw 계층에서 환경변수 RMW_IMPLEMENTATION 하나만 바꾸면 DDS 구현체를 교체할 수 있다." caption="RMW_IMPLEMENTATION 환경변수 하나로 구현체가 바뀐다 — 애플리케이션 코드는 그대로" >}}

**`RMW_IMPLEMENTATION` 환경변수 하나로 구현체를 교체할 수 있다.** 애플리케이션 코드는
한 줄도 바뀌지 않는다. 그래서 순수한 A/B 비교가 가능하다.

### 1-3. DDS가 실제로 하는 일

| 기능 | 설명 | 로봇에서의 의미 |
|---|---|---|
| **디스커버리** | 노드들이 서로를 자동으로 찾음(SPDP/SEDP) | `roscore` 없이 로봇·PC 노드가 자동 연결 |
| **QoS** | 신뢰성·내구성·이력 등 22종 정책 | 센서는 유실 허용(BEST_EFFORT), 맵은 늦게 붙어도 수신(TRANSIENT_LOCAL) |
| **도메인 격리** | `ROS_DOMAIN_ID`로 논리 분리 | 로봇마다 도메인을 나눠 다중 로봇 운용 |
| **직렬화·전송** | CDR 직렬화 + UDP 멀티캐스트/유니캐스트 | 대역폭·지연·CPU 비용이 여기서 발생 |

### 1-4. 두 구현체

| | **Fast DDS** (eProsima) | **Cyclone DDS** (Eclipse) |
|---|---|---|
| ROS 2 Jazzy | **기본값** | 선택 설치 |
| 특징 | 기능 풍부(공유메모리, 디스커버리 서버, XML 프로파일) | 경량·단순, 코드베이스가 작음 |
| 설정 | XML 프로파일 + `ROS_STATIC_PEERS` | `CYCLONEDDS_URI` XML |
| 평판 | 기능성 | **자원 효율** — 이 실험의 가설 |

### 1-5. 왜 이 실험을 했는가

측정 대상 로봇의 상시 부하가 비정상적으로 높았다.

- **정지 상태에서도** Nav2·측위·base 프로세스 합계가 **단일 코어 기준 243%**(4코어의 61%)
- 임무가 추가로 쓰는 건 **+10~27%p뿐**
- 정지 중인데도 노드마다 **초당 150~185회 컨텍스트 스위치** → 계산이 아니라 **통신 대기·깨어남 비용**

계산이 아니라 깨어남이 비용이라면, 미들웨어 교체가 유효한 레버일 수 있다. 그 가설로
A/B 측정을 설계했다.

## 2. 측정 방법

| 항목 | 내용 |
|---|---|
| 대상 | 로봇 1대(동일 하드웨어·동일 코드), **Raspberry Pi 4 Model B** / 4코어 / 3,784 MiB · 최대 1.8GHz |
| 미들웨어 | A = `rmw_fastrtps_cpp`(기본) · B = `rmw_cyclonedds_cpp` 2.2.3 |
| 조건 | ① 정지(임무 없음) ② 순찰 주행 중 ③ 도킹+카메라(AprilTag 검출) |
| 표본 | 조건당 **60초**(도킹만 40초), 1초 간격 |
| 도구 | `mpstat -P ALL`(시스템), `pidstat -u -w`(프로세스별 CPU·컨텍스트 스위치) |
| 부가 | `vcgencmd measure_temp` / `get_throttled`(열 스로틀링), `/proc/loadavg` |
| 통제 | A·B 사이 **재부팅**으로 상태 초기화. 코드·설정·맵·임무 경로 동일 |

**CPU 표기**: 프로세스 CPU는 단일 코어 기준이다. `100%` = 코어 1개 완전 점유이므로
4코어 장비의 총량은 `400%`다. 시스템 사용률(mpstat)은 4코어 평균 백분율이다.

```bash
PIDS=$(pgrep -d, -f "sllidar_node|/bringup|map_server|/amcl|lifecycle_manager|\
controller_server|smoother_server|planner_server|behavior_server|bt_navigator|\
waypoint_follower|velocity_smoother|agent_node|detector|precision_parking")

mpstat 1 60  > /tmp/_mp.$L &                    # 시스템 전체
pidstat -u -w -p "$PIDS" 1 60 > /tmp/_ps.$L &   # 프로세스별 CPU + 컨텍스트 스위치
wait
```

### 기준점 — ROS 스택이 없을 때 (20초)

```text
CPU   user 1.71%   system 1.73%   iowait 0.54%   idle 96.02%
load  0.20 / 0.52 / 0.34      온도 53.5°C      throttled 0x0
메모리 813 / 3,784 MiB
```

**이 기기는 ROS가 없으면 사실상 놀고 있다.** 이후 관측되는 부하는 전부 ROS 스택이
만든 것이다.

## 4. 해석 — 미들웨어 교체는 어디까지 유효한가

### 4-1. 순찰 주행 — CycloneDDS가 유의미하게 낫다

```text
CPU 사용률        78.3%  →  73.4%    (−4.9%p)
user CPU          53.72  →  42.22    (−11.50%p)
프로세스 CPU 합계  270.57 →  236.38   (−34.19%p,  −12.6%)
bt_navigator      36.03  →  23.75    (−12.28%p,  −34%)
idle              21.66% →  26.61%   (+4.95%p 여유 확보)
```

**★게다가 B-2는 불리한 조건에서 이겼다** — 온도 79.8°C(A는 71.1°C), 시작 load 9.72(A는
6.70). 열·부하가 더 나쁜 상태에서도 CPU를 덜 썼다.

### 4-2. 정지 상태 — 상쇄되어 뚜렷하지 않다

```text
프로세스 CPU 합계  243.82 → 220.67   (−23.15%p)   ← 개선
user CPU          46.93  → 39.76    (−7.17%p)    ← 개선
system CPU        21.38  → 29.72    (+8.34%p)    ← 악화
전체 사용률        68.5%  → 71.9%    (+3.4%p)     ← 소폭 악화
```

**user는 줄고 system은 느는 교환**이 일관되게 나타난다. 정지 상태에서는 이 둘이
상쇄된다. 다만 B-1은 79.8°C·load 11.46에서 시작해 A-1(67.6°C·6.18)보다 불리했으므로,
**동일 조건이었다면 격차는 더 좁거나 역전됐을 가능성이 있다.**

### 4-3. 도킹 — 측정 무효 (열 스로틀링)

```text
A-3b  throttled = 0x0        스로틀링 없음
B-3b  throttled = 0xe0008    soft temp limit + 주파수 캡 + 스로틀링 발생
      온도 83.2 → 82.3°C, 배터리 저하 상태
```

스로틀링이 걸리면 같은 부하에서도 처리량이 떨어져 CPU 수치가 왜곡된다. 이 조건은
배터리 충전·냉각 후 재측정 대상이다.

### 4-4. 1차 판정

| 조건 | 판정 | 근거 |
|---|---|---|
| **순찰 주행** | **CycloneDDS 우세** | CPU −4.9%p, 프로세스 합계 −12.6%, 불리한 열 조건에서 달성 |
| 정지 | 판단 유보 | user↓ / system↑ 상쇄, 조건 불일치 |
| 도킹+카메라 | **측정 무효** | 열 스로틀링 발생 |
| 컨텍스트 스위치 | **차이 없음** | 두 구현체 모두 노드당 150~190/s |

**그리고 이 실험은 근본 병목이 DDS가 아님도 함께 보여준다** — detector가 약 142%,
Nav2 스택이 약 133%를 쓰는 구조에서 미들웨어 교체로 얻는 것은 두 자릿수 %p 수준이다.

## 5. 전환하며 밟은 함정 4건

CycloneDDS 전환은 환경변수 하나로 끝나지 않았다. WiFi·다중 인터페이스 환경에서 네 번
막혔다.

### 함정 ① `ROS_STATIC_PEERS`가 디스커버리를 방해

```text
증상  로봇에서는 PC 노드가 보이는데 PC에서는 로봇 노드가 안 보임(비대칭)
원인  Fast DDS 계열 설정. Cyclone 에서는 도움이 안 되고 간섭
조치  Cyclone 을 쓰는 셸에서 unset ROS_STATIC_PEERS
```

### 함정 ② WiFi 멀티캐스트로는 데이터가 전달되지 않음

```text
증상  디스커버리 성공(노드·토픽 목록 보임)인데 topic echo 데이터 0건
원인  Cyclone 기본 AllowMulticast=true → 데이터도 멀티캐스트. WiFi AP가 사실상 차단
조치  AllowMulticast를 spdp 로 (디스커버리만 멀티캐스트, 데이터는 유니캐스트)
      + Peers 에 상대 IP 명시
```

Fast DDS에서 `ROS_STATIC_PEERS`로 유니캐스트를 강제했던 것과 **같은 문제·같은 해법**이다.

### 함정 ③ 인터페이스 고정이 같은 호스트 통신을 끊음

```text
증상  AllowMulticast=false + 원격 피어만 지정 → 로봇 내부 노드끼리도 서로 못 찾음
      (도메인 노드 수 0, /scan 연결 정보 없음 — 스택이 떠 있어도 기능적으로 죽은 상태)
원인  NetworkInterface name="wlan0" 로 고정하면 루프백 경로가 빠짐
조치  인터페이스 고정을 제거하고 AllowMulticast=spdp 로 해결
```

### 함정 ④ 이종 미들웨어는 통신되지 않는다

로봇을 Cyclone으로 바꾸자 **Fast DDS인 관제 PC와 통신이 완전히 끊겼다**(heartbeat 미수신).
ROS 2는 RMW 혼용을 보장하지 않는다. **한 시스템의 모든 참가자를 같은 구현체로 맞춰야
한다.** 이 실험에서도 로봇 15개 프로세스 + PC 콘솔 + 웹앱 백엔드를 전부 전환한 뒤에야
측정이 가능했다. (이 함정은 §8에서 실제 도킹 실패로 한 번 더 돌아온다.)

### 최종 설정

```xml
<?xml version="1.0" encoding="UTF-8"?>
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain id="any">
    <General>
      <AllowMulticast>spdp</AllowMulticast>   <!-- 디스커버리만 멀티캐스트, 데이터는 유니캐스트 -->
    </General>
    <Discovery>
      <Peers><Peer address="상대_IP"/></Peers>
    </Discovery>
  </Domain>
</CycloneDDS>
```

```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml
unset ROS_STATIC_PEERS
```

### 여기까지의 측정 신뢰성

정직하게 남긴다.

1. **A와 B의 열·부하 조건이 완전히 같지 않다.** A는 부팅 17분·67.6°C, B는 재기동 반복 후
   79.8°C에서 시작했다. → **B에 불리한 방향**이므로, 순찰에서 B가 이긴 결과는 보수적으로
   해석해도 유효하다.
2. **도킹(B-3b)은 스로틀링으로 무효**다.
3. 측정 중 `pidstat` 출력 해석에서 두 번 오독이 있었고 원본 데이터로 정정했다 —
   `%CPU`는 8번째 컬럼(4번째는 `%usr`)이고, `-u -w` 동시 출력 시 **Average 블록이 두 개**라
   뒤쪽이 컨텍스트 스위치다. 이 글의 모든 수치는 원본 `pidstat` 파일에서 재추출한 값이다.
4. 각 조건 **1회 측정**이다. 반복 측정으로 분산을 확인하지 않았다.

## 6. 더 큰 레버 — 무엇이 노드를 깨우는가

미들웨어 교체가 두 자릿수 %p 수준이라는 결론에 이어, §3-4의 관찰을 따라갔다 —
컨텍스트 스위치가 미들웨어와 무관하다면, **깨어남은 발행 주기에서 나온다.**

### 6-1. 발행 주기 실측

| 토픽 | 주기 | 비고 |
|---|---:|---|
| **`/tf`** | **67.0 Hz** | 최대 유발원 |
| `/odom` | 30.1 Hz | |
| `/joint_states` | **50.6 Hz** | ★bringup은 30Hz만 내는데 50Hz — 중복 발행자 존재 |
| `/scan` | 10.1 Hz | |

`/tf` + `/odom` + `/scan` = **107회/초**. 여기에 각 노드의 타이머(10~20Hz)와
lifecycle bond(10Hz)를 더하면 관측된 `cswch/s 150~190`과 정확히 일치한다.

★**이것이 과거 튜닝이 실패한 이유도 설명한다.** controller 20→10Hz(+3.27%p), local
costmap 10→5Hz(+1.48%p)로 타이머를 낮췄지만 **지배항인 `/tf` 67Hz를 건드리지 않아**
효과가 없었다([앞선 글의 기각 실험들](../wasab-로봇함대-두-도메인을-잇는-agent와-cpu튜닝/)).

### 6-2. `/tf` 67Hz의 정체, 그리고 발행자가 하나 더 있었다

{{< figure src="/images/diagrams/autodrive-tf-wakeup-sources.svg" alt="노드를 깨우는 발행 주기의 정체. tf 67헤르츠는 pinky_bringup 30헤르츠, robot_state_publisher 약 30헤르츠, amcl 저빈도가 합쳐진 값이고, joint_states 실측 50.6헤르츠는 bringup 30헤르츠 외에 URDF 기반 joint_state_publisher가 20.6헤르츠를 중복 발행한 결과다. 이 중복 노드를 제거하면 tf는 55.9헤르츠, joint_states는 30헤르츠로 떨어지고 프로세스 CPU 합계가 19.01퍼센트포인트 감소한다." caption="깨어남의 지배항은 /tf 67Hz — 그리고 /joint_states에는 값도 틀린 중복 발행자가 붙어 있었다" >}}

`bringup.py`의 **단일 30Hz 타이머**가 TF·odom·joint_states를 한꺼번에 발행한다.

```python
# pinky_bringup/bringup.py:88
self.timer = self.create_timer(1.0 / 30.0, self.update_and_publish)
    → _publish_tf()            odom → base TF
    → _publish_odometry()      /odom
    → _publish_joint_states()  /joint_states
```

그런데 `/joint_states` 실측이 **50.6Hz** — bringup(30Hz) 외에 `joint_state_publisher`
노드가 **20.6Hz를 추가**하고 있었다. 이 노드는 URDF 기반 기본 발행자로,
**엔코더 실측값이 아닌 값**을 낸다. 즉 CPU만 먹는 게 아니라 **틀린 값을 흘리고 있었다.**

## 7. 첫 번째 철회 — 3번째 로봇을 재보니 CPU가 3분의 1

로봇31(3번째 개체)에서 **같은 스택·같은 CycloneDDS·같은 JSP 제거 상태**로 재검증했더니
CPU가 3분의 1로 나왔다. 처음에는 열 스로틀링 탓으로 판단했으나, **하드웨어를 확인하니
보드 세대가 달랐다.**

| | 로봇31 | 로봇44 · 50 |
|---|---|---|
| **보드** | **Raspberry Pi 5 Model B Rev 1.0** | Raspberry Pi 4 Model B Rev 1.5 |
| CPU | Cortex-A76 | Cortex-A72 |
| **최대 클럭** | **2,400 MHz** | 1,800 MHz |
| 측정 시 온도 | 56~59°C | 70~81°C |
| `throttled` | 관측 불가(`/dev/vcio` 없음) | **0x80000** (soft temp limit 이력) |

RPi5는 클럭이 1.33배 높고 A76은 A72 대비 IPC가 크게 앞서, 같은 작업의 `%CPU`가 2~3배
낮게 나온다. ★**이 글 §1~§6의 측정은 전부 RPi4(로봇44·50)** 에서 이뤄졌다.

### 7-1. 동일 조건인데 3배 차이

| 지표 | **로봇31** 정지 | **로봇31** 순찰 | **로봇31** 도킹 | 로봇44 정지 | 로봇44 순찰 | 로봇44 도킹 |
|---|---:|---:|---:|---:|---:|---:|
| **CPU 사용률** | **25.5%** | **26.2%** | **35.2%** | 66.1% | 70.3% | 90.1% |
| user | 16.54 | 17.71 | 25.81 | 32.63 | 36.92 | 55.04 |
| system | 7.89 | 7.58 | 9.41 | 30.90 | 30.86 | 35.07 |
| **idle** | **74.54** | **73.68** | **63.61** | 33.90 | 29.68 | **7.53** |
| **프로세스 CPU 합계** | **81.52** | **92.28** | 87.76 ※ | 221.66 | 245.34 | 302.55 |
| **온도** | **56.8°C** | **57.9°C** | **59.5 → 56.8°C** | 70.6°C | 75.4°C | 77.9 → **81.3°C** |
| load 시작 | 3.18 | 4.32 | 2.64 | 4.21 | 8.30 | 8.69 |

※ 로봇31 도킹은 detector가 측정창을 벗어나 합계에 미포함(시스템 사용률과의 차이 ≈ 53%가

### 7-2. 스택 동작 자체는 동일하다

```text
로봇31   정지  81.52 → 순찰  92.28    +10.76  (+13.2%)
로봇44   정지 221.66 → 순찰 245.34    +23.68  (+10.7%)
```

**주행이 추가로 만드는 부하 비율은 두 로봇이 거의 같다.** 즉 스택 동작 자체는 동일하며,
차이는 전부 **바닥값(상시 비용)** 에 있다.

### 7-3. `tag_lost`는 CPU 부하 문제였다

같은 코드·같은 태그·같은 도킹 절차인데 결과가 갈렸다.

| | 로봇31 | 로봇44 |
|---|---|---|
| 도킹 중 idle | **63.61%** | **7.53%** |
| 상태 전이 | `NAV → SEARCH_TAG → TAG_SERVO_ALIGN → SETTLE → DONE` | `TAG_SERVO_ALIGN → FAILED(tag_lost)` |
| 결과 | **완주** | 실패(육안으로는 정차 성공) |
| 온도 변화 | 59.5 → **56.8°C**(하강) | 77.9 → **81.3°C**(상승) |

→ **CPU 여유가 있으면 정렬 단계를 끝까지 통과한다.** §6-6에서 "원인은 CPU가 아닌 다른
요인(FOV 잘림 등)으로 좁혀진다"고 적었던 추정은 **틀렸다. 정정한다.** 이틀 전
로봇31(load 4.05)이 성공하고 로봇50(load 9~13)이 실패했던 기록과도 일치한다.

### 7-4. 이 발견이 앞선 결론에 미치는 영향

| 결론 | 판정 | 이유 |
|---|---|---|
| **JSP 제거 효과** (−19.01%p) | ✅ **유효** | 동일 로봇·동일 조건 전후 비교 |
| **CycloneDDS 순찰 개선** (−34.19%p) | ✅ **유효** | 동일 로봇 A/B |
| **"정지 상태 4코어의 61% 소비"** | ⚠️ **RPi4 한정** | RPi5에서는 **20%**(81.52/400) |
| **"detector 87.91%"** | ⚠️ **RPi4 기준 상한값** | RPi5에서는 절반 이하로 추정 |
| **`tag_lost` 원인** | ✅ **CPU 여유 부족으로 확정** | §7-3 |
| **서로 다른 로봇 간 절대값 비교** | ❌ **불가** | 보드 세대가 다르면 %CPU 자체가 다른 척도다 |

여기까지의 결론은 명확해 보였다 — **보드 세대가 지배 변수다.** 그런데 4번째 로봇이
이걸 뒤집었다.

## 8. 두 번째 철회 — RPi4로도 도킹은 완주한다

로봇87은 **RPi4이면서 `throttled=0x0`**(스로틀링 이력 없음)인 유일한 개체다.
§7에서 분리하지 못했던 **"보드 세대 vs 열 상태"** 를 가르는 대조군이 됐다.

| 지표 | **로봇31** RPi5 | **로봇87** RPi4 `0x0` | **로봇44** RPi4 `0x80000` |
|---|---:|---:|---:|
| 정지 CPU / 합계 | 25.5% / 81.52 | **61.1% / 215.22** | 66.1% / 221.66 |
| 순찰 CPU / 합계 | 26.2% / 92.28 | **67.4% / 239.07** | 70.3% / 245.34 |
| 도킹 CPU / **idle** | 35.2% / **63.61%** | 79.4% / **20.58%** | 90.1% / **7.53%** |
| 순찰 증가폭 | +10.76 (13.2%) | **+23.85 (11.1%)** | +23.68 (10.7%) |
| 온도(정지→도킹) | 56.8 → 59.5°C | 57.5 → **75.5°C** | 70.6 → **81.3°C** |
| **도킹 결과** | **DONE 완주** | **DONE 완주** ★ | **`tag_lost` 실패** |

### 8-1. 정지 상태에서 열의 기여는 3%뿐

```text
같은 RPi4끼리   정지 215.22 vs 221.66   차이 3.0%   (스로틀링 유무에도 불구)
                순찰 239.07 vs 245.34   차이 2.6%
RPi4 → RPi5     정지 215.22 vs  81.52   차이 62%
```

**정지·순찰의 절대값을 가르는 것은 보드 세대**이고, 열은 3% 남짓이다. 여기까지는
§7의 결론이 맞다.

### 8-2. 그러나 도킹 성패는 열이 갈랐다

{{< figure src="/images/diagrams/autodrive-docking-idle-threshold.svg" alt="도킹 중 CPU idle 여유와 도킹 성패의 관계. RPi5인 로봇31은 idle 63.61퍼센트로 완주, RPi4이면서 스로틀링 이력이 없는 로봇87은 idle 20.58퍼센트로 역시 완주, RPi4이면서 스로틀링 이력이 있는 로봇44는 idle 7.53퍼센트로 tag_lost 실패했다. 임계는 보드 세대가 아니라 CPU 여유다." caption="같은 RPi4인데 결과가 갈렸다 — 정지 측정에서는 3%였던 차이가 도킹에서 성패를 가른다" >}}

**임계는 보드가 아니라 CPU 여유다.** RPi4라도 여유가 20% 남으면 도킹이 완주한다.
§7 초안에서 "보드 교체의 효과가 압도적"이라고 썼던 결론은 **철회한다.** 실용적
우선순위는 **냉각 관리 → detector 최적화 → JSP 제거·미들웨어 튜닝**이며, 보드 교체는
마지막 수단이다.

### 8-3. `sllidar_node` 격차도 재정정

| | 로봇31 RPi5 | 로봇87 RPi4 `0x0` | 로봇44 RPi4 `0x80000` |
|---|---:|---:|---:|
| 정지 | 1.93 | **29.44** | 24.79 |
| 순찰 | 1.93 | **26.99** | 20.41 |

동일 드라이버·동일 10Hz인 `sllidar_node`가 보드 간 12배 차이를 보였을 때, 나는 "세대차
2~3배로는 설명이 안 되니 열 스로틀링이 겹쳤을 것"이라고 썼다. **스로틀링이 없는
로봇87이 오히려 더 높다** — 이 격차는 열이 아니라 **순수한 보드 성능차**다(시리얼
I/O·인터럽트가 잦은 작업에서 A76과 A72의 차이가 더 벌어지는 것으로 보인다).

### 8-4. 부수 확인 — agent만 다른 미들웨어면 도킹이 통째로 멈춘다

로봇87의 1차 도킹은 `nav_timeout`으로 실패했는데, 원인은 성능이 아니었다.

```text
bt_navigator(Nav2)  librmw_cyclonedds_cpp
agent_node          librmw_fastrtps_cpp    ← Cyclone 소싱 안 된 터미널에서 기동
  → agent 가 띄운 precision_parking 도 FastDDS 상속
  → navigate_to_pose 액션 서버를 못 봄 → nav_status=pending 영구 유지
  → 60초 후 NAV_CANCELING → FAILED(nav_timeout), 로봇은 한 번도 안 움직임
```

`/cmd_vel_nav`가 비어 있고 `/scan`·`/amcl_pose`는 정상인 조합이 이 증상의 지문이다.
§5 함정 ④(RMW 혼용 불가)의 구체 사례다. **agent 재기동 후 도킹은 DONE 완주.**

## 9. 최종 우선순위와 다음 단계

{{< figure src="/images/diagrams/autodrive-cpu-priority-revision.svg" alt="CPU 부하 우선순위가 두 번 정정된 과정. 처음에는 detector, Nav2 스택, joint_state_publisher, 미들웨어 순이었고, 3번째 로봇 RPi5로 교차검증한 1차 정정에서는 보드 세대가 맨 앞으로 왔으며, 4번째 로봇인 스로틀링 없는 RPi4가 도킹을 완주하면서 최종 정정에서는 RPi4 냉각 관리가 맨 앞으로 오고 보드 교체는 마지막 수단으로 밀렸다." caption="개체를 하나 더 붙일 때마다 결론이 바뀌었다" >}}

| 레버 | 효과 | 위험 | 비고 |
|---|---|---|---|
| **RPi4 냉각 관리** | 도킹 **성패를 가름** | 없음 | idle 20%를 확보하면 완주. **1순위** |
| **detector 최적화** | 최대 **87.91%** | 미검토 | 해상도·프레임률·검출 주기 |
| **중복 `joint_state_publisher` 제거** | **−19.01%p** | **없음** | 실기 검증 완료. **단, launch 수정으로** |
| CycloneDDS 전환(순찰) | **−34.19%p** | 중 (전 노드 전환 필요) | §4-1 |
| `/tf` 30 → 20Hz (bringup 타이머) | 미측정 | 소 (제어 피드백) | 후속 후보 |
| 미사용 Nav2 서버 제거 | 미측정 | 중 (BT 확인 필요) | waypoint_follower·smoother |
| ~~controller 20→10Hz~~ | **+3.27%p (악화)** | — | **기각됨** |
| ~~local costmap 10→5Hz~~ | **+1.48%p (악화)** | — | **기각됨** |

남은 숙제도 적어 둔다.

1. **냉각·충전 후 3조건 재측정** — 특히 스로틀링으로 무효가 된 도킹+카메라
2. **`lifecycle_manager` 부하 규명** — 관리 프로세스가 실무 노드보다 CPU를 더 쓴다
   (Fast DDS 22.39% · Cyclone 26.67%, 강제 선점 229~281/s로 최다)
3. `vcgencmd get_throttled`를 **운영 점검 항목에 상시 포함** — 측정·판정 전에 먼저 확인
4. 로봇31(RPi5)에 `/dev/vcio` 생성(`sudo mknod /dev/vcio c 100 0`)해 스로틀링 관측 가능하게
5. 반복 측정으로 분산 확인 후 채택 여부 확정

## 10. 정리 — 숫자보다 남은 것

- **정지 상태 부하가 본체였다.** 임무가 아니라 "스택이 떠 있다는 사실"이 4코어의 60%를
  먹었고, 그 원인은 계산이 아니라 **초당 150~190회의 깨어남**이었다.
- **미들웨어 교체는 유효하지만 두 자릿수 %p짜리 레버다.** 순찰 구간 −34.19%p(−12.6%),
  그것도 B에 불리한 열 조건에서 얻은 값이다. 대신 전 노드를 동시에 갈아야 한다.
- **가장 싼 개선은 불필요한 노드를 끄는 것이었다.** 중복 `joint_state_publisher` 하나로
  −19.01%p. 게다가 그 노드는 CPU만 먹은 게 아니라 **엔코더가 아닌 값을 흘리고 있었다.**
  그리고 **kill이 아니라 launch를 고쳐야** 재기동 후에도 유지된다.
- **한 대로 내린 결론은 함대에서 살아남지 못한다.** 3번째 로봇이 "보드 세대가 전부"라고
  말했고, 4번째 로봇이 그걸 다시 뒤집어 **"임계는 CPU 여유"** 로 바꿨다. RPi4라도
  idle 20%가 남으면 도킹은 완주한다.
- **틀린 추론을 두 번 지웠다.** `tag_lost`의 원인을 FOV로 좁힌 것도, 라이다 노드 격차를
  열 탓으로 돌린 것도 반증됐다. 측정을 늘리는 일의 값어치는 새 숫자가 아니라 **이미 쓴
  결론을 지울 수 있다는 것**에 있다.

같은 로봇들의 다른 기록도 함께 보면 맥락이 이어진다 —
[로봇 함대를 한 화면에서](../wasab-로봇함대-두-도메인을-잇는-agent와-cpu튜닝/),
[AprilTag PID 정밀 도킹 성공 기록](../nav2-apriltag-pid-정밀도킹-성공기록/),
[Nav2·costmap·AMCL 입문](../nav2-costmap-amcl-자율주행-위치추정-입문/).

## 부록. 재현 방법

```bash
# 1) 설치
sudo apt install ros-jazzy-rmw-cyclonedds-cpp

# 2) 설정 (로봇·PC 양쪽, 상대 IP만 다르게)
cat > ~/cyclonedds.xml <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<CycloneDDS xmlns="https://cdds.io/config"><Domain id="any">
  <General><AllowMulticast>spdp</AllowMulticast></General>
  <Discovery><Peers><Peer address="192.168.2.5"/></Peers></Discovery>
</Domain></CycloneDDS>
EOF

# 3) 전환 (스택을 띄우는 모든 터미널에서)
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml
unset ROS_STATIC_PEERS

# 4) 실제 적용 확인 — 환경변수가 아니라 로드된 라이브러리로 검증
grep -o "librmw_[a-z_]*" /proc/<PID>/maps | sort -u

# 5) 원복
unset RMW_IMPLEMENTATION CYCLONEDDS_URI   # 후 스택 재기동
```

측정 원본은 `/tmp/dds_<라벨>.txt`·`/tmp/_mp.<라벨>`·`/tmp/_ps.<라벨>`에 남겼는데,
**`/tmp`는 재부팅 시 초기화된다.** A 시리즈 원본은 재부팅으로 소실됐고 이 글의 수치가
유일한 기록이다 — 측정 결과는 `/tmp` 바깥에 저장할 것.
