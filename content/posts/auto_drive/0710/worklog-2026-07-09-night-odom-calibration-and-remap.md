# Worklog — .87 odom 캘리브레이션 + 재-SLAM(wasab_map11) (2026-07-09 밤)

로봇 **.87**(오늘 낮 작업은 `.31`), 도메인 **50**.
선행: `docs/worklog-2026-07-09-amcl-localization-root-cause.md` (§0에서 "다음 세션 1순위 = 재-SLAM" 결론).

## 0. 결론 (먼저 읽기)

- **재-SLAM 완료 → `wasab_map11`.** `/scan` 대조에서 **평균 2.4 cm, 최대 3.0 cm**. `map5`는 평균 5.7, 최대 10.3 cm였다. **네 방향 오차 부호가 모두 같아(등방)** 위치를 밀어내지 않는다 — `map5`의 비대칭 오차가 AMCL을 12 cm 끌어당기던 것과 대비된다.
- **성공의 열쇠는 맵이 아니라 `.87`의 odom 캘리브레이션이었다.** `wheel_separation`이 틀려 회전이 **+3.9%** 과대보고됐고, 그래서 첫 재-SLAM 맵이 전단(shear)·이중 벽으로 망가졌다.
- **캘리브레이션 결과**: `wheel_radius 0.028 → 0.0273`, `wheel_separation 0.0961 → 0.0976`. 검증: 직진 1 m **−0.15%**, 제자리 360° **−0.06%**.
- **미완**: 회전 점프량(맵 품질의 최종 지표) 측정 실패. `.87`의 **`/odom` 값이 간헐적으로 얼어붙는 현상** 때문. 내일 여기서 재개.

## 1. 왜 `.87`인가 / 낮 작업과의 관계

낮에는 `.31`로 측위 오차를 추적해 "맵의 벽 위치가 실제와 2~10 cm 다르다"는 결론에 도달했다. 밤에 사용자가 **`.87`로 로봇을 바꾸고** 새 맵을 만들기 시작했다.

**중요**: `.31`에서 검증한 것(odom 정확도)이 `.87`에도 성립한다고 가정한 것이 초반 실수였다. 두 로봇의 `bringup.py`는 **서로 다른 버전**이다.

| | `.31` | `.87` |
|---|---|---|
| 휠 상수 | 모듈 상수 `WHEEL_RAD = 0.028` | `declare_parameter('wheel_radius', 0.027)` |
| 값 출처 | 코드 하드코딩 | **3곳**: `bringup.py` 기본값 / `bringup_robot.launch.xml` `<arg default>` / `config/pinky_params.yaml` |
| 우선순위 | — | launch `<param>` 이 코드 기본값을 **덮어씀** |

`bringup.py`만 고치고 재기동했는데 값이 안 바뀌어 한참 헤맸다. **세 곳을 모두 맞춰야 한다.**

## 2. 첫 재-SLAM 실패 — 전단(shear)과 이중 벽

`mapper_params_wasab.yaml`(벤더 파일 복사본)으로 `resolution 0.05→0.02`, `minimum_travel_distance 0.5→0.1`, `minimum_travel_heading 0.5→0.2` 적용 후 두 바퀴 주행.

결과: 맵이 사선으로 흘러내리고 같은 벽이 두 겹(`#.#`, `##.##`)으로 찍혔다.
```
벽 bbox = 1.300 × 2.140 m      (실제 1.00 × 1.95)
```

기각한 원인:
- **CPU 부족** — `load 1.12`, `/scan` 10 Hz 안정, `slam_toolbox`는 CPU 상위 5위에도 없음. 기각.
- **라이다 TF** — `.31`과 동일(`-0.017, 0, 0.125`, yaw 180°). 기각.

## 3. ★ 원인 = `.87` odom 회전 오차

### 3.1 직진 검증 (1.000 m)
| | odom | 오차 |
|---|---|---|
| `wheel_radius = 0.027`(원래) | — | (미측정) |
| `wheel_radius = 0.028` | 1.0238 m | **+2.4%** |

### 3.2 회전 검증 (제자리 360°)
`~/yaw_trace.py` 신규 작성 — yaw를 **언랩해 누적 회전각**을 적산(360° 회전 시 시작·끝 yaw 차이는 0이므로 증분을 더해야 한다). 병진도 같이 기록해 제자리성 확인.

```
실제 360.00°  →  odom +374.13°   (+3.9%)
병진 0.03 cm  (슬립 없음 → 각도 신뢰 가능)
```

### 3.3 두 측정으로 두 상수를 연립으로 푼다
odom 거리 ∝ `r`, odom 각도 ∝ `r / B`.
```
직진:  1.0238 = r_cfg / r_true          →  r_true = 0.028 / 1.0238 = 0.02735
회전:  1.0392 = 1.0238 × (B_true / 0.0961) →  B_true = 0.0961 × 1.0151 = 0.09755
```
적용값: **`wheel_radius = 0.0273`, `wheel_separation = 0.0976`**

**기하학적 반경 ≠ 유효 구름반경.** 바퀴 지름 실측은 56 mm(→ 0.028)지만 하중을 받은 타이어가 눌려 실제 구름반경은 54.7 mm다. 실측으로만 알 수 있다.

**교차검증**: `.31`은 `r = 0.028`에서 직진 `+2.7%` → 유효반경 `0.02726`. **두 로봇이 0.0273으로 일치.** 우연이 아니다.

### 3.4 보정 후 재검증
```
직진 1.000 m  →  odom 0.9985 m   (−0.15%)   [보정 전 +2.4%]
회전 360.00°  →  odom 359.79°    (−0.06%)   [보정 전 +3.9%]
```

**회전 3.9% 과대보고의 의미**: 로봇이 90° 돌 때 odom은 93.5°라고 말한다. SLAM은 그 각도로 스캔을 얹으므로 벽이 3.5°씩 어긋난 자리에 그려지고, 두 바퀴 돌면 같은 벽이 두 겹으로 찍힌다. §2의 그림 그대로다.

## 4. 재-SLAM 성공 — `wasab_map11`

`minimum_time_interval: 0.5 → 0.1` 추가(라이다 10 Hz인데 0.5초 게이트가 5장 중 1장만 통과시키고 있었다). 두 바퀴 주행.

```
105 × 62 px @ 0.02 m/pix,  origin [-0.191, -0.207]
자유공간 1.960 × 1.020 m     실제 1.95 × 1.00     오차 +1 / +2 cm
외벽 두께 3셀 = 6 cm         (map10 은 안쪽으로 10 cm 번짐)
이중 벽 없음 (내부 칸막이 양면은 정상)
```

### 4.1 `/scan` 대조 — 맵 품질 판정
AMCL이 믿는 pose에서 맵에 광선을 쏘아 `/scan`과 비교(순환 없음: 둘 다 '지금'의 관측).

| 방향 | 라이다 | 맵 기대값 | 오차 |
|---|---|---|---|
| front | 1.010 | 0.984 | **+2.6 cm** |
| right | 0.126 | 0.104 | **+2.2 cm** |
| left | 0.888 | 0.858 | **+3.0 cm** |
| rear | 0.199 | 0.180 | **+1.9 cm** |

**평균 2.4 cm, 최대 3.0 cm.** (`map5`: 평균 5.7, 최대 10.3 cm / 부호가 `+8.0, +2.1, +10.3, −2.2` 로 제각각)

**부호가 모두 같다(등방 +2 cm)** — 점유 셀 중심과 실제 벽면의 반 셀 차이로 설명된다. **등방 오차는 위치를 밀어내지 않는다.** `map5`의 비대칭 오차가 AMCL을 한쪽으로 12 cm 끌어당기던 것과 결정적으로 다르다.

## 5. 미완 — 회전 점프량 측정 실패

맵 품질의 **최종 지표**(재측위 후 좌90°+우90°에 AMCL이 얼마나 밀리는가)를 못 쟀다.

```
로그:  odom  (-0.007206, 0.002039) → (-0.007143, 0.001918)   변화 0.1 mm
       map   ( 0.272379, 0.039404) → ( 0.109003, 0.006477)   변화 16.6 cm
       yaw   64.8° → 0.87°                                    변화 −64°
```
바퀴가 안 돌았다는데 AMCL이 16 cm 이동·64° 회전했다고 한다. **`/odom` 값이 얼어 있다.**

```
/odom 발행 30 Hz 정상,  값은 -0.007122 로 완전히 동결
/scan 10 Hz 정상,  배터리 7.15 V,  load 2.95,  bringup 노드 생존
```

`.87`에서 **오늘 세 번째**다. 앞선 두 번(회전 시험 중 412샘플·750샘플 동결)은 "타이밍 문제"로 넘겼으나, 같은 증상이 반복되므로 **별개 결함일 가능성이 높다.**

미확인 사항 (내일 첫 질문):
- 그 회전 동안 로봇이 **물리적으로 움직였는가**
- 그사이 RViz `2D Pose Estimate`를 **다시 찍었는가** (AMCL 점프의 다른 설명)

## 6. 부수 발견 — DDS/RViz

- **RViz 세그폴트**: `nav2_view.rviz` 설정을 로드하다 죽는다(`exit code -11`). Nav2를 내린 상태에서 costmap/voxel 디스플레이가 원인. **설정 없이 `rviz2` 로 띄우고 Map/LaserScan/TF 를 수동 추가**할 것.
- **`ap0` 다중 인터페이스**: `sudo ip link set ap0 down` **만으로는 부족**하다. 주소가 남아 있으면 그 뒤에 뜬 노드가 여전히 광고한다. `sudo ip addr flush dev ap0` 까지 하고 **노드를 재기동**해야 깨끗해진다. 양방향 `ROS_STATIC_PEERS`(PC↔로봇) 병행.
- **기동 순서**: `bringup` → `localization`. 역순이면 `/odom` 부재로 `amcl`이 넘어진다(실제로 죽음).
- **`/map` 은 latched**(transient_local). `ros2 topic echo` 기본 QoS로는 못 받는다. `--qos-durability transient_local` 필요.

### AMCL (`.31`, `map5`, 낮 작업)
| 항목 | 값 |
|---|---|
| `alpha 0.4` + recovery 활성 → 1 m 직진 추적 | **0.785 m (−21.5%)** |
| `alpha 0.2` + recovery 0.0 → 1 m 직진 추적 | **0.997 m (−0.3%)** |
| 제자리 180° 회전(빠름/느림/`alpha4=0.05`) | 12.0 / 12.2 / 10.9 cm — **속도·alpha 무관** |
| 같은 자리 2회차 회전 | **0.9 cm** → 누적 아님, **1회 점프 후 포화** |
| 재측위 직후 AMCL vs 벽 실측 | 2.3 ~ 5.2 cm |
| 회전 많은 이동 뒤 AMCL 오차 | 최대 **31 cm** |

**해석**: 회전은 원인이 아니라 **방아쇠**. AMCL은 `update_min_d/a = 0.05`라 정지 중 갱신하지 않다가, 회전이 갱신을 촉발하면 **스캔이 말하는 자리로 1회 점프**하고 머문다. 그 점프량 = 태그/초기pose가 말하는 위치 ↔ 스캔 평형점의 차이 = **맵 품질의 지표**.

### 태그 / 카메라 (`.31`)
| 태그 | 등록 좌표 | 맵의 벽면 | 벽 뒤로 |
|---|---|---|---|
| 7 | x −0.217 | −0.137 | 8.5 cm |
| 8 | x +0.956 | +0.863 | 9.8 cm |

**재측위에서는 상쇄되어 안 드러난다**: `재측위 pose = 태그_map좌표 ⊖ 카메라가_본_태그`, 같은 +9 cm가 양변에 들어감.

### 기각된 가설 (오늘 하루)
```
pinky odom 25% 과소보고        → 기각 (실측 +2.7%). 메모리의 "해석"이었지 관측이 아니었음
WHEEL_RAD / PULSE_PER_ROT 오류 → 기각 (실측 일치, 멀티턴 처리 정상)
맵 스케일 압축                 → 기각 (map5 벽 간격 실측 1.00 m 일치)
map5 vs map6 차이              → 무관 (가운데 방 벽 한 줄 5 cm 차이뿐)
AMCL 180° 뒤집힘               → 철회 (사용자가 로봇을 손으로 옮긴 것을 몰랐음)
회전 자체가 오차를 만든다        → 기각 (2회차 0.9 cm, 포화)
라이다 레버암(-0.017) 오류      → 기각 (실측 일치)
alpha4                        → 기각 (0.2→0.05 에 12.0→10.9 cm)
스캔 왜곡 / 타임스탬프 지연     → 기각 (회전 속도 3~4배 낮춰도 12.2 cm)
SLAM 전단이 CPU 부족 탓         → 기각 (load 1.12, scan 10 Hz 안정)
```

### 안전 (`.31`, 낮)
- **pinky base 에 `cmd_vel` 워치독이 없다.** Dynamixel 속도모드가 마지막 RPM을 영구 유지 → **발행자를 죽여도 로봇은 안 선다.** 서보 중 SIGTERM 주입 실험에서 로봇이 벽에 충돌.
- `precision_parking.stop()` 의 zero 발행은 `_safe_publish` 의 `rclpy.ok()` 가드에 걸려 SIGINT 시점엔 **조용히 버려진다**(죽은 안전코드).
- 고아 자식 회수(`c207a71`)는 **동작 확인**(SIGTERM +0.5 s 에 그룹 3개 전부 소멸). 다만 그것만으로는 로봇이 멈추지 않는다.

## 9. 교훈

1. **로봇마다 코드가 다르다.** `.31`에서 검증한 odom을 `.87`에도 유효하다고 가정했다. 두 `bringup.py`는 다른 버전이었고, 휠 값이 세 파일에 흩어져 있었다.
2. **값이 여러 곳에 있으면 우선순위를 확인하라.** `declare_parameter` 기본값은 launch `<param>` 에 진다. 고쳤는데 안 바뀌면 로드된 값을 `ros2 param get` 으로 확인할 것.
3. **직진만 검증하고 회전을 안 재면 반쪽이다.** SLAM 전단은 회전 오차에서 왔다. 이동로봇 odom은 `r`과 `B` 두 상수이고, 시험도 두 개(직진·회전) 필요하다.
4. **기하학적 반경 ≠ 유효 구름반경.** 자로 잰 56 mm가 맞아도 실제 구름반경은 54.7 mm다.
5. **"완료" 신호를 받고 기록기를 끄면 늦거나 이르다.** 두 번 헛돌았다. **기록기를 끄지 말고 로그만 읽을 것.**
6. 사원수 부호 반전(`w: + → −`)은 **360° 회전의 물증**이다. yaw만 보면 제자리로 보인다.
7. 손으로 옮기면 odom이 0이다(모터가 속도 0 토크로 바퀴를 잠금). 측정·등록은 반드시 텔레옵 주행.
